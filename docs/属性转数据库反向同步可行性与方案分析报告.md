> **文档状态**：分析结论已核对源码，待决策
> **文档版本**：v1.0
> **核对日期**：2026-10-09
> **目标工程**：思源笔记插件 · 属性管家 (`siyuan-property-manager`)
> **核对依据**：思源本体源码 `../siyuan`（Go 内核 + `app/src` 前端）、本机 `developer_docs/`
>
> 说明：本文所有内核行为均逐条核对源码，不采信推测。冲突时以 `../siyuan` 源码为准（本机 `developer_docs/` 存在一处已发现的失准，见附录 B）。

---

## 1. 背景与问题

插件提供「由笔记块一键生成思源原生数据库（属性视图 / Attribute View，下称 AV）」的能力：扫描带有同一组 `custom-*` 属性的块，建表并把这批块绑定为数据库的行，再将属性值回填进单元格。

由此产生一个自然诉求：

> **属性 → 数据库之后，如果用户在数据库里编辑或新增条目，能否反向同步回块的属性？**

本文回答三件事：**能不能做**、**内核提供了什么**、**推荐怎么做**。

---

## 2. 结论摘要（TL;DR）

1. **能实现，但必须由插件自己实现。思源内核不提供任何「数据库列 ↔ 块属性」的同步通道。**
2. 插件现有代码中存在一个**不成立的假设**：把 AV 列名写成 `custom-xxx` 就以为能与块的自定义属性「原生关联」（`src/components/AttrTemplateGroups.vue:396`）。核对的结论是：**列名只是字符串，内核既不识别该约定，也没有「列名 → 属性名」的映射，更没有 `keyType = "block attribute"` 这类列类型。**
3. AV 的单元格值**只存在 AV 自己的 JSON 里**，与块的 IAL 是两份独立存储，双向都不自动同步。
4. **「新增数据库条目」默认没有回写目标**：在数据库里直接新建的行是游离行（detached，未绑定任何块），因此「新增条目 → 同步回属性」在语义上是空的，需要先明确目标（不支持 / 自动建块并绑定）。
5. 技术上可行的部分（编辑**已绑定行**的单元格 → 回写该块属性）所需的读写与触发能力**都已具备**，缺口集中在：**类型转换、防环、冲突仲裁、游离行处理**。

## 3. 内核机制核对（事实清单）

| # | 事实 | 出处（`../siyuan`） |
| --- | --- | --- |
| F1 | AV 是独立 JSON 存储：`{DataDir}/storage/av/<avID>.json` | `kernel/av/av.go:1391-1405`（`GetAttributeViewDataPath`）、`:951`（`SaveAttributeView`） |
| F2 | 列类型枚举共 17 种，**没有**「块属性」这一类型 | `kernel/av/av.go:158-176`（`type KeyType string`） |
| F3 | 内核中**不存在**「AV 列名 → `custom-*` 属性名」的映射函数 | 全量检索 `kernel/` 与 `app/src` 的动态 `"custom-" + …` 拼接，命中项均与 AV 无关 |

| F5 | 反向同理：`setBlockAttrs` / `batchSetBlockAttrs` 只改节点 IAL 并重建索引，**不触碰任何 AV** | `kernel/model/blockial.go:220-259`、`:137-218` |
| F6 | AV 路径中**唯一**写入 IAL 的是**绑定标记**：`custom-avs`、`custom-av-names`，以及块键静态锚文本 `custom-sy-av-s-text-<avID>` | `kernel/model/attribute_view.go:8508-8542`（`unbindBlockAv`）、`:8619-8649`（`bindBlockAv0`）、`:8651-8670`；常量见 `kernel/av/av.go:1426-1430` |

| F9 | 各类型列（text/number/date/select/mSelect/url/email/phone/mAsset/checkbox/relation/rollup）的值**全部**只存在于 AV JSON，与 IAL 无关 | 同上 F4；`kernel/av/value.go` 各 `Value*` 结构 |
| F10 | 读取时可从 IAL 派生的仅限：块键静态文本、`created`/`updated`（取自块 IAL）、模板列（可引用任意 IAL 键，仅渲染期计算，**不回写**） | `kernel/sql/av.go:589-618`、`:621-702`、`:343-395` |
| F11 | AV 的变更 op **会全端广播**（不受"排除自身"限制） | `kernel/api/transaction.go:385-394`（`shouldBroadcastAttrViewTransactions`） |
| F12 | 但 op 顶层 `blockID` 是**数据库载体块**（AV 容器），`rowID` 是**行记录 ID**，**都不是源块 ID** | `app/src/protyle/render/av/cellValue.ts:177-192`；`kernel/model/attribute_view.go:8013-8030`（载体块用于 `avParseView`/`avSaveView`） |
| F13 | 新增行的 op 为 `insertAttrViewBlock`，`srcs[].isDetached` 决定是否绑定块；在数据库内直接新建的行是**游离行** | `kernel/model/attribute_view.go:5989-6008`、`:6126-6131`；前端 `app/src/protyle/render/av/addToDatabase.ts:28-40` |
| F14 | 块 IAL 变更走另一条信号：`transactions` 中的 `updateAttrs` op | `kernel/model/blockial.go:538-551`（`pushBlockAttrs`） |
| F15 | HTTP 写入接口名字有误导性：`/api/av/batchSetAttributeViewBlockAttrs` 实际写的是 **AV store，不是块属性** | `kernel/api/av.go:572-589` → `model.BatchUpdateAttributeViewCells` |

**一句话总结**：AV 与块属性是**两套互不感知的存储**，中间没有任何自动桥。所谓「用 `custom-` 前缀命名列即可原生关联」是一个**未被内核支持的假设**。

## 4. 本插件侧现状

### 4.1 建表实现（`src/components/AttrTemplateGroups.vue`）

`createDatabaseFromSelection()`（`:455`）的手工建表流程：

| 步骤 | 调用 | 行号 |
| --- | --- | --- |
| 1 | 属性键规范化为 `custom-*` | `:470-473` |
| 2 | `putFile('/data/storage/av/<avID>.json', avJson)` —— **手写 AV JSON** | `:478` |
| 3 | `insertBlock({ dataType:'dom', data:'<div data-type="NodeAttributeView" …>' })` | `:485-490` |
| 4 | `await sleep(300)` 等待内核索引 | `:496` |
| 5 | `addAttributeViewBlocks({ avID, srcs })`，`srcs` 为 `{ id, isDetached: false }` | `:499-500` |
| 6 | `getFile(...)` 回读，构建 `blockIdToRowIdMap[block.id] = blockID` | `:508-520` |
| 7 | `sql(...)` 查 `attributes` 表 → `batchSetAttributeViewBlockAttrs` 回填 | `:526-545` |

**要点与隐患**：

- **列名刻意等于源属性键**（`:389-403`，`name` 存带 `custom-` 前缀的 fullKey），注释声明意图是"实现原生关联"——**该意图不成立**（见第 3 节）。
- **列类型被硬编码为 `text`**（`:394-404`，`numberFormat: ''`），单选/多选/日期/数字全部降级为文本，**往返必然丢类型**。
- **回填只在建表时执行一次**（步骤 7），此后没有「属性 → 数据库」的持续传播。
- **潜在错写**：`:535` 的 `blockIdToRowIdMap[row.block_id] || row.block_id` 兜底，在映射缺失时会拿**块 ID 当行 ID**传给 `batchSetAttributeViewBlockAttrs`，属于静默错写，应改为跳过并告警。
- 手写 AV JSON（步骤 2）字段易与内核版本漂移，建议后续改用官方建表接口。

### 4.2 行与块的绑定

- 行**确实绑定到真实块**：`isDetached: false`，且主键 `block` 列的每行值持有真实 `block.id`（`:508-520`）。
- 因此 **行 → 块的反查是可物化的**：既可从 AV JSON 读，也可经 `renderAttributeView` 读（见 4.3）。

### 4.3 现有可复用的读/写能力

| 能力 | 位置 | 用途 |
| --- | --- | --- |
| `renderAttributeView(id, pageSize=9999)` | `src/api.ts:101-103` | **读全量 AV**；`useNotebookDbStats.ts:99-118` 已示范解析 `view.columns`（含 `type`）与 `view.rows[].cells[].value`，其中 block 列值为 `{ block: { id } }` |
| `setBlockAttrs(id, attrs)` | `src/api.ts:29-34` | 回写块属性的写入原语 |
| `getBlockAttrs(id)` | `src/api.ts:36-40` | 幂等比对 |
| `onWsMain`（`ws-main`） | `src/index.ts:100-143` | **唯一变更入口**；现状按 `op.id \|\| op.blockID` 收集并派发 `spm:attrs-changed` |
| `spm:attrs-changed` → `reload()` | `useAttrPanel.ts:127-135`、`useBlockAttrs.ts:48-82` | 面板刷新链路 |
| `chainWrite` 串行化 | `useBlockAttrs.ts:89-98` | 同键写入防乱序 |

### 4.4 现存缺口（反向同步不存在）

全仓检索 `setBlockAttrs` 仅两处调用者，**均与 AV 无关**：`useBlockAttrs.ts:112,184`（面板手改）、`useNotebookAttrStats.ts:107,115`（统计页批量改，数据源是 `attributes` SQL）。唯一读 AV 的 `useNotebookDbStats.ts:97` 是**只读**的。

**并且现有 `onWsMain` 对 AV 编辑天然失效**：AV op 的顶层 `blockID` 是**载体块**（F12），因此 `spm:attrs-changed` 会为 AV 容器触发，**永远不会为被绑定的源块触发**。反向同步必须自带触发分支，不能靠现有链路搭便车。

## 5. 可行性判定

| 环节 | 结论 | 说明 |
| --- | --- | --- |
| **读**：定位被改的行 → 源块 | ✅ 可行 | `renderAttributeView` 已能拿到行、列类型与 block 列 `block.id` |
| **读**：取出该行的列值 | ✅ 可行 | 同上，`view.rows[].cells[]` |
| **写**：写回块属性 | ✅ 可行 | `setBlockAttrs` 现成 |
| **触发**：感知 AV 变更 | ✅ 可行，需新增分支 | `onWsMain` 加 AV 识别（`op.avID` 或 action 含 `attrview`），按 avID 防抖 |
| **类型转换** | ⚠️ 需自建 | 建表时列全为 `text`；且需按 schema `resolveAttrType` 反向序列化 |
| **防环** | ⚠️ 需自建 | 回写块属性会触发 `updateAttrs`（F14）与 `spm:attrs-changed` |
| **冲突仲裁** | ⚠️ 必须定规则 | 见第 8 节，这是**最大风险** |
| **游离行（新增行）** | ❌ 无回写目标 | 见第 6 节 |

## 6. 关键前提：「编辑 / 新增条目」分三种，回写目标完全不同

| 情形 | 有无绑定块 | 能否回写属性 | 说明 |
| --- | --- | --- | --- |
| 编辑**已绑定行**的单元格 | 有 | ✅ 可以 | 反向同步的主场景 |
| 在数据库里**新增一行** | 无（detached） | ❌ **无目标** | 语义上无对应块，见下 |
| 新增并**绑定已有块** | 有 | ✅ 可以 | 等价于第一类 |

> **「新增条目 → 反向同步到属性」在默认情况下是空的**：新建行不绑定任何块，没有块属性可写。
> 两种处理方式需二选一：
> - **不支持**（推荐起步）：仅同步绑定行，UI 提示游离行不同步；
> - **自动建块并绑定**：为游离行插入新块并 `bindBlockAv`，属于较大改动，且会产生新块与新的绑定标记（F6/F8）。

## 7. 方案选项对比

| 方案 | 做法 | 优点 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 事件驱动单向镜像**（推荐） | 监听 AV op → 按 avID 防抖 → `renderAttributeView` → 逐行取 `block.id` 与 `custom-*` 列 → 与 `getBlockAttrs` 比对后仅回写差异 | 复用现成封装；改动集中在一个新 composable + `onWsMain` 一个分支；只覆盖绑定行，边界清晰 | 与"面板改属性"冲突（第 8 节）；类型需转换 |
| **B. 双向同步** | 在 A 之上补「属性 → AV」写回（`batchSetAttributeViewBlockAttrs`，需 `keyID` + `itemID`） | 语义完整，两边都能改 | 需冲突仲裁 + 双份防环；AV JSON 手写易碎；复杂度约翻倍 |
| **C. 反转事实源** | 面板对已绑定块**直接读 AV** 的值，不做镜像 | 无冲突、无环，天然一致 | 推翻插件属性模型（模板、统计、批量重构均基于 IAL / `attributes` 表），改动面最大 |
| **D. 按需同步** | 打开面板或点「同步」时 diff 一次 | 最可控，无后台开销，无防环难题 | 不满足"自动反向同步"的直觉预期 |

## 8. 最大风险：冲突与"回写覆盖"

内核没有「属性 → AV」的通道（F4/F5），因此单向镜像存在**必然的覆盖问题**：

> 用户在插件属性面板里改了 `custom-status`
> → **AV 里仍是旧值**（内核不会同步过去）
> → 下一次该 AV 发生任何变更触发镜像时
> → 旧值被反写回属性，**静默覆盖用户刚才的修改**。

可选仲裁规则（建议实现前先定）：

1. **方向约定 / 开关**：默认仅「AV → 属性」，并在 UI 明确提示「转库后请以数据库为维护入口」；
2. **时间戳仲裁**：镜像额外写入 `custom-av-sync-ts`，与块 IAL 的 `updated` 比较，只让更新的一侧生效；
3. **降级为方案 D**：把冲突交给用户，手动触发同步。

另有一类**性能**风险：`renderAttributeView` 按 `pageSize = 9999` 全量读取，大表下每次变更都全表拉取，需按 avID 防抖并考虑规模上限。

## 9. 推荐落地路径（分阶段）

### Phase 0 — 修正误导与隐患（小改动，建议先做）

- 删除或改写 `AttrTemplateGroups.vue:396` 中"列名可与块属性原生关联"的注释（不成立）。
- 修复 `:535` 的 `|| row.block_id` 兜底错写，改为映射缺失时跳过并告警。
- 视情况：把列类型从硬编码 `text` 改为按 schema 写入正确 `keyType`（否则往返必丢类型）。

### Phase 1 — 只读 POC（不写回，先验证）

- 在 `onWsMain` 增加 AV 分支：识别 `op.avID`／action 含 `attrview`（F11/F12），按 avID 防抖。
- `renderAttributeView(avID)` 取行，用 block 列的 `block.id` 建**行 → 块**映射（不可用 `rowID` 冒充块 ID，F7/F12）。
- **仅在控制台打印**「行 → 块 + 各 `custom-*` 列值」的 diff，验证捕获准确性与映射正确性。**先不写任何数据。**

### Phase 2 — 反向写回（方案 A）

- 幂等：先 `getBlockAttrs` 比对，仅写差异。
- 类型转换：按 `resolveAttrType(key)` 把 AV 单元格值反序列化为 IAL 字符串（多选 `", "` 连接、日期 `YYYY-MM-DD`、checkbox `'true'/'false'`，与现有序列化约定一致）。
- 只同步 `custom-*` 列；跳过 `block` / `created` / `updated` / `rollup` / `template` / `lineNumber` 等系统或内部列。
- 防环：写入期间把 `blockId` 记入"预期变更集"，忽略随后 1–2 秒内该块的 `updateAttrs` / `spm:attrs-changed`。
- 串行化：写入经 `chainWrite` 同类机制串行，避免乱序。
- 按第 8 节落地一条仲裁规则。

### Phase 3 — 可选增强

- 双向同步（方案 B）；
- 游离行自动建块并绑定（第 6 节）；
- 改用手写 AV JSON 为官方建表接口，降低版本漂移风险。

## 附录 B：`developer_docs/` 已发现的一处失准

`developer_docs/04-database-av/AV增删改查与参数模型.md:29` 称「`itemID`：行唯一标识（原 `rowID`，**绑定块时该值等于块 `id`**）」。

源码与此不符：前端 `app/src/protyle/render/av/addToDatabase.ts:13-17, 108-111` 传入 `itemID: Lute.NewNodeID()`（新生成的 ID），内核 `kernel/model/attribute_view.go:6070-6085` 亦自行分配 `srcItemID`，与 `boundBlockID = src["id"]` 相互独立（`:6171-6182`）。

**结论：实现时必须从 block 列的 `block.id` 解析绑定块，绝不能假设 `itemID === block.id`。**（附带说明：内置示例数据中两者恰好相等，容易造成误判。）
