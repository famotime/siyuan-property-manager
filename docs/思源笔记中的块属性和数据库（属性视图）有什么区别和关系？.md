# 思源笔记中的块属性和数据库（属性视图）有什么区别和关系？

思源笔记里的**块属性**是挂在单个内容块上的键值元数据；\*\*数据库（属性视图，Attribute View）\*\*则是一套独立的、带字段类型和视图的结构化数据表。两者可以互相衔接：块可作为数据库的行（条目），数据库也能把块属性作为收集/筛选条件。[^1_1][^1_2]

## 核心区别

| 维度 | 块属性 | 数据库 / 属性视图 |
| :-- | :-- | :-- |
| 本质 | 单个块上的 `key=value` 元数据 | 由字段（列）、条目（行）、视图组成的结构化数据集合 |
| 存储位置 | 块的 IAL / `attributes` 数据表 | 独立的 `.av` 文件与属性视图数据结构，内核称 Attribute View [^1_3][^1_2] |
| 字段类型 | 基本上都是字符串键值对 | 有文本、数字、日期、单选/多选、资源、关联、模板等字段类型 [^1_4] |
| 使用方式 | 给某个段落、标题、任务块打标或补充信息 | 管理任务、项目、文献等一批同构对象，可排序、筛选、汇总 |
| 展示能力 | 通常通过查询、嵌入块或 SQL 使用 | 表格、列表、画廊、看板等多种视图 [^1_2] |
| 关系能力 | 本身没有字段类型和跨表关联模型 | 支持关联字段、汇总、多视图和更复杂的数据组织 [^1_4] |
| 典型例子 | `progress=30`、`priority=2`、`custom-doing=true` | “任务库”：状态、截止日期、负责人、所属项目、优先级 |

块属性由用户通过块标菜单设置，自定义属性名会自动加 `custom-` 前缀；它们适合轻量的标记和检索。[^1_1]

## 两者的关系

可以把它们理解为：

```text
内容块（Block）
 ├── 自身内容：一段文字、标题、任务等
 ├── 块属性：progress=30, priority=2
 └── 可被数据库收集为一条“行/条目”

数据库 / 属性视图（Attribute View）
 ├── 字段：状态、日期、优先级、负责人
 ├── 条目：一行通常对应一个块或一个数据对象
 └── 视图：表格 / 看板 / 画廊 / 列表
```

也就是说，**块属性是“块的元数据”，数据库是“结构化数据容器”**。数据库中的条目可以绑定到内容块；此时块是这条数据的“主键块”或来源块，数据库字段则提供比普通块属性更强的类型、展示和计算能力。[^1_2]

## 什么时候用哪个

- **用块属性**：只需要给零散块打轻量标签，例如 `status=done`、`review=true`，或配合 SQL / 查询块筛选内容。[^1_3][^1_1]
- **用数据库**：需要统一管理一批对象，例如任务、书摘、项目、文献；需要日期、选项、关联、汇总、看板或画廊视图。[^1_4][^1_2]
- **两者结合**：先给块设置自定义属性，再用数据库的自动化/收集规则，把符合笔记本、文档、块类型、标签或自定义属性条件的块收进数据库。[^1_2]


## 一个实用例子

假设你在做开发任务管理：

- 给某个任务段落设置块属性：`custom-status=doing`、`custom-priority=high`。
- 建一个“开发任务”数据库，字段包括：任务名、状态、优先级、截止日期、所属项目。
- 将该任务块加入数据库后，它成为数据库的一行；数据库里的“状态”“优先级”字段可以比裸块属性更好地控制选项、排序和看板展示。
- 后续还可以用数据库的收集规则，自动把带有特定块属性或标签的任务块收进该数据库。[^1_2]

简言之：**块属性偏“给块贴结构化标签”，数据库偏“把一批块或对象组织成可管理的数据表”**；数据库是更高层、更类型化和更可视化的组织方式，块属性则是更底层、更轻量的块级元数据。[^1_4][^1_1][^1_2]

# 如何自动把带有特定块属性或标签的任务块收进数据库？块属性的字符串键值对，如何匹配数据库字段的不同类型？

思源数据库**没有像 Notion 那样开箱即用的“按任意块属性/标签自动收集”规则**；官方数据库的核心操作仍是把块手动添加为条目，再通过字段、筛选、视图管理数据。 要实现自动收集，通常用 **SQL 查询块做动态视图**，或用 **插件 / RunJS / API 定期把匹配块写入数据库**。[^2_1][^2_2][^2_3]

## 三种实现路径

| 方案 | 是否真正写入数据库 | 适用场景 | 维护成本 |
| :-- | :-- | :-- | :-- |
| 手动“添加到数据库” | 是 | 少量、需要长期跟踪的任务 | 低 |
| SQL / 嵌入块动态查询 | 否，只实时展示匹配块 | 只想“看到”带某属性或标签的任务 | 低 |
| API / 插件自动添加条目 | 是 | 需要“任务库”有字段、看板、汇总、关联 | 中高 |

### 1. 手动收集

在任务块上打开块标菜单，选择“添加到数据库”，选择目标数据库即可。之后该块成为数据库条目，可在表格、看板、画廊等视图中管理。[^2_4][^2_1]

适合任务数量不多、且你希望人工确认哪些内容进入任务库的情况。

### 2. 用 SQL 做动态“收集视图”

如果目标只是让带有特定标签或自定义属性的块自动出现在一个列表里，不必写入数据库，可以用嵌入块 / 查询块执行 SQL。思源运行时通过 SQLite 索引笔记数据，`blocks` 表包含块内容与 IAL 属性，`attributes` 表保存从块 IAL 提取的键值对；标签则存于 `blocks.tag`。[^2_2][^2_5]

示例：找出带 `#task#` 标签的块：

```sql
SELECT id, content, tag
FROM blocks
WHERE tag LIKE '%#task#%'
```

示例：找出自定义属性 `custom-status = doing` 的块：

```sql
SELECT b.id, b.content, a.name, a.value
FROM blocks b
JOIN attributes a ON b.id = a.block_id
WHERE a.name = 'custom-status'
  AND a.value = 'doing'
```

> 注意：实际表间字段名以你当前思源版本的 SQLite 结构为准；`attributes` 表的核心思路是“块 ID + 属性名 + 属性值”。[^2_6][^2_2]

这种方式是**动态查询**：任务块加上 `#task#` 或 `custom-status=doing` 后，查询结果会随之变化，但它不会自动成为数据库条目，也不会获得数据库字段值。[^2_7]

### 3. 用 API / 插件自动写入数据库

若确实要“自动收进数据库”，流程是：

1. 用 SQL 或查询 API 找到符合条件的块，例如 `custom-task=true` 或标签 `#task#`。[^2_5][^2_2]
2. 调用属性视图 API，把块 ID 添加为数据库条目。数据库由 `avID` 标识，条目与块绑定后可继续设置各字段的类型化值。[^2_3][^2_4]
3. 将块属性字符串转换后写入对应数据库字段，例如把 `custom-priority=high` 写入“优先级”单选字段。[^2_3]
4. 用定时任务、思源启动钩子、RunJS 插件或外部脚本周期执行；同时记录已导入的块 ID，避免重复添加。

社区 API 文档显示，可通过 `/api/av/setAttributeViewBlockAttr` 按 `avID`、字段 `keyID`、行 `itemID` 和类型化值设置单元格；这里的 `itemID` 是数据库行 ID，不是普通块 ID。[^2_3]

## 块属性如何映射字段类型

块属性本质是字符串键值对；数据库字段则有明确类型，因此写入时必须做**解析和校验**。数据库支持文本、数字、单选、多选、日期、资源、复选框、链接等类型。[^2_8]


| 块属性示例 | 建议数据库字段 | 转换规则 | 失败处理 |
| :-- | :-- | :-- | :-- |
| `custom-note=需要复查` | 文本 | 原样写入 | 一般不会失败 |
| `custom-priority=3` | 数字 | `Number("3")`，校验是否为有限数值 | 非数字则留空或写入文本字段 |
| `custom-status=doing` | 单选 | 值必须匹配已有选项，或先创建选项 | 未匹配则创建选项、留空或记录错误 |
| `custom-tags=ai,terminal` | 多选 | 按分隔符拆分为 `["ai", "terminal"]` | 空值跳过；选项不存在时可自动创建 |
| `custom-due=2026-10-30` | 日期 | 解析为思源可接受的日期/时间值 | 无法解析则留空 |
| `custom-done=true` | 复选框 | `"true"`、`"1"`、`"yes"` 视为真；其余视为假 | 建议只用 `true/false` |
| `custom-url=https://...` | 链接 | 校验 URL 格式后写入 | 非法 URL 留空 |
| `custom-file=20260101120000-xxx.png` | 资源 | 需要使用资源路径/资源 ID 的目标格式 | 不建议直接把任意文本塞入资源字段 |

单选适合状态、优先级这类唯一分类；多选适合标签、关键词等可同时存在多个值；日期适合截止时间；复选框适合完成与否。[^2_8]

## 推荐的任务属性设计

为了让自动同步更稳定，建议块属性使用**机器友好、取值固定**的格式：

```text
custom-task=true
custom-status=doing
custom-priority=high
custom-due=2026-10-30
custom-tags=ai,terminal
```

对应数据库字段：


| 块属性 | 数据库字段 | 字段类型 |
| :-- | :-- | :-- |
| 主块内容 | 任务名 / 主键 | 块 / 文本 |
| `custom-status` | 状态 | 单选 |
| `custom-priority` | 优先级 | 单选 |
| `custom-due` | 截止日期 | 日期 |
| `custom-tags` | 标签 | 多选 |
| `custom-done` | 已完成 | 复选框 |

自定义属性名会由思源自动加 `custom-` 前缀，因此查询和 API 调用时也要使用带前缀的完整属性名。[^2_9][^2_10]

## 实践建议

- **只是筛选展示**：用 SQL / 嵌入块，不要写入数据库；它最轻、最实时。[^2_2][^2_7]
- **需要看板、日期、汇总、关联**：用数据库，并通过 API 或插件同步。[^2_1][^2_3]
- **不要把块属性当作数据库字段本身**：块属性适合作为“入选条件”和轻量元数据；入库后应把数据维护在数据库字段中，避免两处状态不一致。
- **同步脚本要幂等**：先查询该块是否已是数据库条目，或维护 `custom-synced=<avID>` 属性，防止重复添加。[^2_3]

# 什么是全局属性？解决什么问题？有什么使用场景？

**全局属性**指的是在工作空间级别统一定义、可被多个块或多个数据库复用的属性。它解决的核心问题是：当前思源的自定义块属性是“每块各自写字符串”，数据库字段又是“每个数据库各自定义”，容易造成同名属性拼写不一致、类型不一致、选项不统一。[^3_1][^3_2]

需要注意的是，截至目前的思源官方功能中，**“全局属性”更多是一个社区提出的数据模型/功能诉求，而不是像块属性、数据库那样已经完全成熟的官方一等概念**。现有最接近的能力是自定义块属性、标签和数据库字段；社区插件或外部同步脚本可以模拟部分全局属性行为。[^3_2][^3_1]

## 与现有属性的关系

| 层级 | 现有机制 | 是否全局 | 主要限制 |
| :-- | :-- | :-- | :-- |
| 块级 | 自定义块属性，如 `custom-status=doing` | 属性名可重复使用，但定义不集中 | 无统一类型、选项和命名规范 [^3_3][^3_4] |
| 文档/块级 | 标签 `#task#` | 可跨块搜索和导出 | 不是强类型字段，选项管理较弱 [^3_5][^3_1] |
| 数据库级 | 数据库字段，如“状态”“截止日期” | 仅在该数据库内定义和使用 | 跨数据库复用和统一维护较弱 [^3_1] |
| 工作空间级 | **全局属性（理想模型）** | 一次定义，多处复用 | 官方尚未作为完整功能普遍提供 [^3_1][^3_2] |

## 它解决什么问题

### 1. 命名不一致

你可能在一个数据库里写 `status`，另一个里写 `state`，块属性里又写成 `custom-status`。全局属性会要求先注册一个唯一属性，例如：

```text
status
类型：单选
选项：todo / doing / done / blocked
```

之后所有块、数据库都可以引用同一个 `status`，而不是各写各的。[^3_2]

### 2. 类型不一致

块属性本质是字符串，`priority=3`、`priority=高`、`priority=high` 都能写进去；数据库字段虽有类型，但不同数据库里的“优先级”可能类型或选项不同。全局属性可以统一声明：

```text
priority
类型：单选
选项：low / medium / high
```

这样能避免同一概念在不同位置有不同数据形态。[^3_2]

### 3. 选项集中维护

例如任务状态从 `doing` 改名为 `in-progress`，理想情况下只需修改全局属性中的选项定义，相关视图、筛选和展示可随之更新；而不必逐个数据库、逐个块属性去改。社区讨论中正是把这种“一处定义、多处生效”视作全局属性的核心价值。[^3_1]

### 4. 跨库查询与反向查找

有了统一属性后，可以问：

- 工作空间中所有 `status=blocked` 的任务有哪些？
- 哪些数据库使用了 `owner` 属性？
- 哪些块带有 `review=true`？

这比在每个数据库里分别筛选更接近“知识库级”的结构化检索。[^3_6][^3_1]

## 典型使用场景

### 任务管理

定义全局属性：

```text
status：todo / doing / done
priority：low / medium / high
owner：人员或页面引用
due：日期
```

然后让“开发任务库”“内容创作库”“个人待办库”共用这些属性。这样你可以在一个全局视图中查所有 `status=doing` 的事项，无论它来自哪个数据库。[^3_1]

### 阅读与文献管理

统一定义：

```text
source-type：book / paper / video / web
rating：1-5
topic：AI / 前端 / 产品 / 方法论
read-status：unread / reading / finished
```

书摘、论文笔记、视频笔记可以共享同一套元数据，后续按主题、评分或阅读状态聚合。[^3_2]

### 项目与知识库治理

给文档或重要块加：

```text
project：项目 A / 项目 B
area：开发 / 产品 / 运维
review=true / false
archive=true / false
```

这适合把散落在多个笔记本中的资料，按统一维度检索、归档或生成仪表盘。[^3_6]

## 在当前思源中的落地方式

| 目标 | 当前可行做法 |
| :-- | :-- |
| 统一命名 | 制定属性命名规范，如 `custom-status`、`custom-priority`，并写入模板 |
| 统一选项 | 用固定字符串值，例如 `todo/doing/done`，配合 SQL 查询 |
| 跨库筛选 | 用 SQL / 嵌入块查询 `attributes` 表或 `blocks.tag` [^3_7][^3_5] |
| 强类型与视图 | 在每个数据库中建立同名字段，或用脚本同步字段定义 |
| 自动写入 | 通过思源 API / 插件，把块属性转换为数据库字段值 [^3_8] |

例如，你可以约定：

```text
custom-status = todo | doing | done
custom-priority = low | medium | high
custom-area = dev | product | ops
```

再用查询块检索：

```sql
SELECT b.id, b.content, a.value
FROM blocks b
JOIN attributes a ON b.id = a.block_id
WHERE a.name = 'custom-status'
  AND a.value = 'doing'
```

这能在当前版本中近似实现“全局属性”的检索效果，但还不能像真正的全局属性那样集中管理类型、选项和反向关系。[^3_7][^3_1][^3_2]

## 与数据库字段如何选择

- **属性只用于标记、筛选、自动化触发**：优先用统一规范的自定义块属性或标签。
- **属性需要日期、选项、汇总、看板、关联**：使用数据库字段。
- **同一概念要跨多个数据库复用**：目前用“统一命名 + 脚本/插件同步”模拟全局属性；未来若官方支持全局属性，则应把状态、优先级、负责人、领域这类高频维度提升为全局属性。[^3_1][^3_2]

一句话：**块属性是“块上的字符串标签”，数据库字段是“某个表里的列”，全局属性则是“整个工作空间共享的列定义”**；它想把前两者的优点结合起来——既轻量、可挂在块上，又类型化、可复用、可集中维护。[^3_1][^3_2]

# 数据库（属性视图）的使用场景是什么？可以解决什么问题？

思源数据库（属性视图，Attribute View）适合管理**一批具有相同结构、需要持续更新和多维检索的对象**，例如任务、项目、书籍、文献、灵感、人脉或内容选题。它解决的不是“记笔记”，而是“把笔记中的对象变成可筛选、可排序、可关联、可多视角查看的数据”。[^4_1][^4_2][^4_3]

## 它解决什么问题

普通笔记和块引用擅长记录与连接信息，但当你有几十、几百个同类对象时，会遇到这些问题：


| 问题 | 普通笔记 / 块引用 | 数据库 |
| :-- | :-- | :-- |
| 找“所有进行中的任务” | 依赖搜索、标签或人工翻找 | 按状态字段筛选 [^4_2] |
| 按截止日期排序 | 不方便 | 日期字段排序 [^4_3] |
| 给对象加类型化信息 | 块属性只是字符串 | 数字、日期、单选、多选、资源等字段 [^4_2][^4_3] |
| 同一数据换视角查看 | 基本只能看原文 | 表格、看板、画廊等视图 [^4_2] |
| 建立“任务—项目—人员”关系 | 依赖链接，难以结构化追踪 | 关联字段连接不同数据库或块 [^4_1][^4_2] |
| 汇总统计 | 需要额外查询 | 可对数字、日期等字段进行汇总计算 [^4_2] |

简言之，数据库把“散落的块”升级为“有字段、有状态、有关系的记录”。[^4_2][^4_3]

## 典型使用场景

### 1. 任务与项目管理

这是最常见场景。你可以建一个“任务库”，字段包括任务名、状态、优先级、负责人、截止日期、所属项目。

```text
任务名：完成数据库同步插件
状态：doing
优先级：high
负责人：time
截止日期：2026-10-30
所属项目：思源工具链
```

之后可以用看板按“状态”拖动任务，用表格按“截止日期”排序，或筛选出所有高优先级任务。任务管理类集成也通常把任务作为属性视图中的结构化行来管理，并为其建立名称、状态、优先级、日期等字段。[^4_4]

### 2. 项目与任务的多表关联

建立两个数据库：

```text
项目库：项目名、负责人、开始日期、状态
任务库：任务名、状态、截止日期、所属项目
```

在任务库中用关联字段指向项目库，就能从某个项目查看其全部任务，也能从任务反查所属项目。双向关联还能让两边互相看到关联记录。[^4_1][^4_2]

适合个人开发项目、客户项目、研究课题或多团队协作。

### 3. 阅读与文献管理

建一个“文献库”或“阅读库”，字段可包括：

```text
标题、作者、来源类型、主题、评分、阅读状态、笔记链接、标签
```

- 用“阅读状态”筛选未读、在读、已读；
- 用“主题”或“标签”聚合某一领域的资料；
- 用“评分”排序高质量内容；
- 用关联字段连接“书籍库”“概念库”“文章库”。[^4_1]

适合论文阅读、技术资料收集、书摘管理和研究素材库。

### 4. 内容创作与选题库

如果你写博客、做视频或维护开源项目文档，可以建：

```text
选题库：标题、类型、平台、状态、优先级、发布日期、素材链接
```

用看板管理“灵感 → 调研中 → 写作中 → 已发布”，用画廊视图浏览封面或素材，用日期字段安排发布节奏。数据库的画廊、看板等视图正是为同一批记录提供不同工作视角。[^4_2]

### 5. 知识条目与概念库

把“概念”“工具”“模式”“命令”做成数据库，例如：

```text
工具库：名称、类别、平台、许可证、价格、官网、评价
```

你可以筛选“开源 + 支持 macOS + 免费”的工具，或按类别浏览终端、AI 编程、部署、笔记类工具。配合思源的双链和 SQL 查询，还能把数据库条目嵌入到相关笔记中。[^4_3]

### 6. 人脉、会议与决策记录

- **人脉库**：姓名、组织、角色、联系方式、最近联系日期、关联项目；
- **会议库**：主题、时间、参会人、决议、后续行动；
- **决策库**：决策名、背景、选项、结论、负责人、复审日期。

这类场景的关键不是写长文，而是让每条记录都有稳定字段，方便日后追踪和复盘。[^4_4][^4_2]

## 什么时候不该用数据库

| 情况 | 更合适的做法 |
| :-- | :-- |
| 只是记录一篇技术笔记、教程或思考过程 | 普通文档 |
| 只想给几个块打标记 | 自定义块属性或标签 |
| 只想临时筛选某些内容 | SQL / 嵌入块查询 [^4_3] |
| 对象之间没有共同字段，也不需要反复筛选 | 不必强行建表 |
| 需要复杂表格计算、外部系统同步、多人并发协作 | 数据库可承担部分能力，但可能仍需外部工具或 API 集成 [^4_5][^4_4] |

## 判断标准

适合建数据库的信号通常有三个：

1. **同构**：记录有相似字段，例如每个任务都有状态和截止日期。
2. **持续变化**：状态、日期、负责人、评分会随时间更新。
3. **需要多视角**：既要表格总览，也要看板执行、画廊浏览或按项目关联查看。[^4_3][^4_2]

一句话：**数据库适合“对象库”，不适合“文章库”**。当你在反复问“所有 X 中，哪些满足 Y、按 Z 排序、和哪个项目相关”时，就该把它做成属性视图数据库。[^4_2][^4_1]

# 数据库和普通表格有什么区别？各有什么试用场景？

普通表格是**文档里的静态排版结构**，适合展示对照关系；数据库是**结构化记录集合**，适合持续管理一批对象。思源数据库的“表格视图”虽然长得像普通表格，但底层是字段、行、筛选、排序和视图系统，而不是单纯的 Markdown 表格。[^5_1][^5_2][^5_3]

## 核心区别

| 维度 | 普通表格 | 数据库 / 属性视图 |
| :-- | :-- | :-- |
| 本质 | 文档中的行列排版 | 由字段（列）、条目（行）、视图组成的数据集合 [^5_3] |
| 单元格内容 | 主要是文本、数字等展示内容 | 有类型化字段：文本、数字、日期、单选、多选、资源、关联等 [^5_3] |
| 行的含义 | 通常只是表格中的一行内容 | 一条记录，可绑定到一个块或页面 [^5_2][^5_3] |
| 排序 / 筛选 | 手动调整，或依赖查询 | 可按字段排序、筛选、查询 [^5_2][^5_3] |
| 视图 | 只有这一种表格形态 | 同一数据可用表格、看板、画廊等不同视图查看 [^5_4][^5_5] |
| 数据复用 | 主要服务于当前文档阅读 | 可作为任务库、项目库、文献库等长期数据源 [^5_6][^5_3] |
| 关联能力 | 无原生记录级关联模型 | 可通过关联字段连接其他数据库或块 [^5_6][^5_3] |
| 修改成本 | 改格式容易，改数据结构较麻烦 | 增删字段、调整视图较系统化 [^5_3] |
| 典型例子 | “Windows / macOS / Linux 功能对照表” | “开发任务库：任务、状态、负责人、截止日期” |

## 普通表格适合什么

普通表格适合**一次性、静态、以阅读为目的**的信息呈现。

- 功能或产品对比：例如“Warp、WezTerm、wterm 的快捷键、AI 能力、价格对比”。
- 配置参数说明：例如“环境变量、默认值、说明、是否必填”。
- 技术方案对照：例如“方案 A / 方案 B / 方案 C 的成本、部署难度、可维护性”。
- 简单清单：例如“依赖包、版本、用途”。
- 教程中的步骤或术语说明。

它的优点是轻、直观、嵌入文档自然；缺点是行不是“记录”，列不是“字段”，很难长期按状态、日期、负责人等维度维护。[^5_7][^5_1]

## 数据库适合什么

数据库适合**同构、持续更新、需要检索和多视角管理**的信息。

- **任务库**：任务名、状态、优先级、负责人、截止日期；用看板跟踪执行进度。[^5_3][^5_5]
- **项目库**：项目名、阶段、负责人、开始/结束日期、关联任务。
- **文献 / 阅读库**：标题、作者、主题、评分、阅读状态、笔记链接。
- **工具库**：工具名、类别、平台、许可证、价格、官网、评价。
- **内容选题库**：标题、类型、状态、发布日期、素材链接。
- **人脉 / 会议库**：姓名、组织、最近联系时间、关联项目、后续行动。[^5_6][^5_3]

数据库的关键价值在于：同一批记录可以按不同字段筛选、排序，并切换为表格、看板、画廊等视图；这是普通表格做不到的。[^5_4][^5_5][^5_3]

## 一个对照例子

同样是记录终端工具：

### 普通表格：适合“选型对比”

| 工具 | 平台 | AI 能力 | 开源 | 适用场景 |
| :-- | :-- | :-- | :-- | :-- |
| Warp | macOS / Linux / Windows | 有 | 部分开源 | AI 终端与团队协作 |
| WezTerm | 跨平台 | 无 | 是 | 高性能本地终端 |
| wterm | Web / 本地集成 | 可扩展 | 视项目而定 | Web 终端与自定义集成 |

这类表格的目的是**帮你做一次决策**，之后通常不需要频繁更新每行的状态。[^5_7]

### 数据库：适合“工具资产库”

| 字段 | 示例 |
| :-- | :-- |
| 名称 | Warp |
| 类别 | 终端 |
| 平台 | 多选：macOS、Linux、Windows |
| 许可证 | 单选：专有 / 开源 |
| 评价 | 数字：4.5 |
| 状态 | 单选：试用中 / 已采用 / 弃用 |
| 官网 | 链接 |
| 相关笔记 | 关联块或文档 |

当你持续试用、评估、替换工具，并希望按“平台 = macOS”“许可证 = 开源”“状态 = 试用中”筛选时，数据库更合适。[^5_2][^5_3]

## 选择规则

- **只为了在文章里对比或说明**：用普通表格。
- **行会不断增加、字段会反复更新**：用数据库。
- **需要按状态、日期、类别筛选或排序**：用数据库。[^5_2][^5_3]
- **需要看板、画廊等不同视角**：用数据库。[^5_5][^5_4]
- **需要和其他对象建立稳定关联**：用数据库。[^5_3][^5_6]
- **数据只是临时展示，不需要长期维护**：用普通表格。[^5_7]

一句话：**普通表格是“文档中的表”，数据库是“笔记里的数据表”**。前者优化阅读和对比，后者优化记录、追踪、筛选和多视图管理。[^5_1][^5_3]

# 思源的表格能直接转成数据库吗

**思源原生目前没有内置的“普通表格一键转数据库”功能**；普通表格块和数据库块是两种不同类型的块，数据库数据还存放在独立的属性视图文件中，因此不能靠简单改块类型完成转换。[^6_1][^6_2]

不过可以通过**插件、Quicker 动作或 API 脚本**实现转换：读取表格的表头和每一行，创建数据库字段与条目，再把单元格值按字段类型写入。社区已有 `siyuan-table-to-database` 插件和“表格文件转思源数据库”的 Quicker 动作提供这类能力。[^6_3][^6_4]

## 原生能力现状

| 方式 | 是否支持 | 说明 |
| :-- | :-- | :-- |
| 右键普通表格 → 转为数据库 | 否 | 官方没有该菜单/原生转换功能 [^6_1] |
| 复制表格粘贴为数据库 | 否 | 粘贴通常仍按表格或文本处理，不会自动建立字段类型 |
| 插件转换 | 是 | 可解析表格并生成数据库，支持类型推断和主列选择 [^6_4] |
| CSV / Excel 转数据库 | 是，通过工具 | Quicker 动作可将 CSV、XLS、XLSX 转为思源数据库 [^6_3] |
| API 脚本转换 | 是 | 读取表格块内容后，通过属性视图 API 创建字段和行 [^6_1][^6_4] |

## 推荐转换流程

如果你要转换，建议按下面的流程做，避免类型和列名出错：

1. **检查表格结构**：第一行必须是表头；每一行应是一条独立记录；避免合并单元格。Markdown 表格本身不支持合并单元格，复杂表格应先拆平。[^6_5]
2. **确定主键列**：通常选名称、标题、任务名这类唯一或接近唯一的列。Quicker 方案也要求第一列作为数据库主键。[^6_3]
3. **确定字段类型**：文本、数字、日期、单选、多选、复选框、链接等不能都按文本处理，否则后续无法排序、筛选或统计。[^6_4][^6_3]
4. **执行转换**：使用插件或脚本创建数据库，将表头映射为字段、数据行映射为条目。[^6_4]
5. **人工校对**：重点检查日期、数字、多选分隔符、复选框值和链接是否正确解析。[^6_3]

## 插件方案

`siyuan-table-to-database` 插件的核心能力是：

- 将任意普通表格一键转换为可筛选、可排序的数据库；
- 转换前显示列名和推断出的类型；
- 允许逐列覆盖类型、选择主列；
- 支持文本、数字、复选框、单选、多选、网址、邮箱、电话、日期等类型推断。[^6_4]

这最适合你已经有一张结构良好的思源普通表格，希望保留数据并升级为任务库、工具库、文献库等场景。

## CSV / Excel 方案

如果数据原本在 Excel、Google Sheets 或 CSV 中，通常不必先粘成思源表格再转；可直接用“表格文件转思源数据库”类工具导入。该方案支持设置数据库名称和列类型，包括文本、数字、单选、多选、日期、链接、邮箱、手机、勾选框等；多选列还需指定分隔符，例如逗号或空格。[^6_3]

## 手写 API 转换的注意点

思源的数据库块在 `.sy` 文件中只保存 `AttributeViewID` 等引用信息，实际属性视图数据在伴随的独立数据文件中；官方格式文档也明确提示不要凭空构造数据库块或其 ID。[^6_1]

因此，脚本转换不应直接改 `.sy` 文件，而应通过内核 API：

1. 创建属性视图 / 数据库；
2. 添加字段并指定类型；
3. 添加条目；
4. 按字段类型写入单元格值；
5. 将生成的数据库块插入目标文档。[^6_1][^6_3]

## 什么时候值得转

| 表格特征 | 建议 |
| :-- | :-- |
| 只是一次性对比，之后不再更新 | 保留普通表格 |
| 有状态、日期、优先级等会变化的列 | 转数据库 |
| 需要按列筛选、排序、看板展示 | 转数据库 [^6_6][^6_4] |
| 表格有合并单元格、复杂嵌套内容 | 先整理成规范的一行一记录，再转换 [^6_5] |
| 数据已在 Excel / CSV 中且规模较大 | 直接用 CSV / Excel 转数据库工具 [^6_3] |

一句话：**能转，但通常要借助插件或脚本；原生思源不会把普通表格自动识别为数据库字段和记录。** 如果表格会长期维护，转换通常值得；如果只是文档内的一次性对照表，保留普通表格更简单。[^6_1][^6_4][^6_3]

# 管理账号信息是一种使用数据库的推荐场景吗？有什么最佳实践？

**不建议把账号密码直接放在思源数据库里**。思源数据库适合管理账号的“非敏感目录信息”，例如服务名、用途、负责人、到期时间、文档链接；真正的密码、API Key、恢复码应放在专用密码管理器中，思源数据库只保存指向该密码管理器条目的引用。NIST 也明确建议使用密码管理器保存和生成密码，并为密码管理器本身启用 MFA。[^7_1][^7_2]

## 为什么不建议存密码

思源笔记是本地优先的知识库，但它的数据库、文档、附件和同步数据本质上都是工作空间内可被读取、备份、导出或同步的文件；一旦设备失窃、同步配置泄露、备份外流或 API Token 泄露，明文凭据的风险会显著放大。密码管理器则专门围绕加密保险库、随机密码生成、自动填充和跨设备同步设计。[^7_3][^7_4]


| 数据类型 | 是否适合放思源数据库 | 推荐存放位置 |
| :-- | :-- | :-- |
| 服务名称、用途、环境 | 适合 | 思源数据库 |
| 负责人、状态、到期时间 | 适合 | 思源数据库 |
| 登录网址 | 适合 | 思源数据库或密码管理器 |
| 用户名 | 谨慎 | 密码管理器为主 |
| 密码 | 不适合 | 密码管理器 |
| API Key / Secret | 不适合 | 密码管理器或密钥管理服务 |
| 2FA 恢复码 | 不适合 | 密码管理器安全备注 / 离线加密备份 |
| 助记词、私钥 | 绝不适合 | 硬件钱包 / 冷备份，且避免联网设备长期保存 |

OWASP 也强调密码绝不能以明文存储；对个人账号而言，把明文密码写进笔记、表格或普通文本文件都会显著增加泄露后的影响面。[^7_5][^7_6]

## 推荐的思源数据库设计

可以建一个“账号资产台账”，只记录元数据，不记录秘密：


| 字段 | 类型 | 示例 |
| :-- | :-- | :-- |
| 服务名称 | 文本 | Cloudflare |
| 用途 | 单选 | 域名 / 邮件 / 部署 / 数据库 |
| 环境 | 单选 | 生产 / 测试 / 个人 |
| 负责人 | 文本或关联 | time |
| 状态 | 单选 | 使用中 / 已停用 / 待轮换 |
| 到期时间 | 日期 | 2027-03-01 |
| 密码管理器条目 | 链接 | `bitwarden://...` 或条目 ID |
| 相关文档 | 关联 / 链接 | 部署文档、DNS 配置笔记 |
| 最后审计日期 | 日期 | 2026-10-23 |
| 备注 | 文本 | 仅记录非敏感注意事项 |

这样数据库解决的是“我有哪些账号、谁负责、什么时候到期、相关文档在哪”；密码管理器解决的是“凭据本身如何安全保存、生成和填充”。[^7_1][^7_3]

## 最佳实践

1. **密码和密钥只进密码管理器**：使用 Bitwarden、1Password、KeePassXC 等专用工具；为每个服务生成唯一、随机的长密码，避免复用。[^7_2][^7_1]
2. **思源只存引用，不存秘密**：在数据库中保存密码管理器条目链接、条目 ID 或内部编号，而不是密码本身。
3. **为密码管理器启用强主密码和 MFA**：优先使用 FIDO2 / Passkey 或硬件密钥等抗钓鱼方式；密码管理器是所有凭据的单点入口，必须重点保护。[^7_3][^7_1]
4. **分离“账号台账”和“凭据库”**：思源数据库负责治理、审计、到期提醒；密码管理器负责机密存储。
5. **标记密钥轮换状态**：用“待轮换 / 已轮换 / 已泄露处理中”等状态字段管理 API Token、数据库密码、云平台密钥。
6. **避免在思源中粘贴敏感内容**：包括终端命令中的 Token、`.env` 内容、数据库连接串、云厂商 Secret；如必须记录配置结构，用占位符代替。
7. **限制同步和备份范围**：即使只存元数据，也应确认哪些笔记本会同步、备份到何处；敏感台账最好放在受控工作空间或本地优先的笔记本中。
8. **定期审计**：按季度或按项目检查账号是否仍在使用、负责人是否正确、密钥是否过期、是否需要撤销访问。
9. **不要把主密码写进思源**：主密码或恢复码不应以明文形式保存在任何笔记、数据库或云端文档中。[^7_6][^7_7]

## 例外情况

如果只是管理**低敏感、可公开或容易重置的账号元数据**，例如“哪些服务用了哪个邮箱注册、订阅何时到期、文档在哪里”，思源数据库是很好的场景。

但如果涉及：

- 云平台 Root 账号；
- 生产数据库密码；
- 服务器 SSH 私钥；
- 域名注册商账号；
- 支付、身份认证、代码仓库管理员账号；
- API Secret、OAuth Client Secret、JWT 签名密钥；

应一律使用密码管理器、密钥管理服务或硬件安全方案，思源中最多保留“存在哪个保险库、条目编号是什么”的索引。[^7_8][^7_3]

一句话：**思源数据库可以做“账号资产管理台账”，但不要做“密码保险库”**。把可检索、可审计的元数据交给思源，把真正机密交给专用密码管理器，是兼顾可用性和安全的分工。[^7_2][^7_5][^7_1]

# 思源的关联字段怎么和账号管理结合

思源的**关联字段**可以把“账号台账”和其他数据库连接起来，让账号不再只是孤立的一行，而是能挂到**负责人、项目、服务器、域名、订阅、密钥轮换任务**等对象上。它适合做账号资产的治理视图，但仍不应把密码或 API Secret 放进思源。[^8_1][^8_2]

## 推荐的数据库结构

以个人开发者或小团队的云资源管理为例，建议拆成几个数据库，而不是把所有信息塞进一张表：

```text
账号库
 ├── 服务名称、用途、环境、状态、到期时间
 ├── 负责人 → 关联「人员库」
 ├── 所属项目 → 关联「项目库」
 ├── 关联资源 → 关联「资源库」
 └── 轮换任务 → 关联「任务库」

项目库
 ├── 项目名、阶段、负责人
 └── 相关账号 → 由账号库反向关联

资源库
 ├── 资源名、类型、环境、区域
 ├── 所属项目 → 关联「项目库」
 └── 使用账号 → 关联「账号库」

任务库
 ├── 任务名、状态、截止日期
 └── 关联账号 → 关联「账号库」
```

关联字段的作用是让一个账号能同时指向多个对象，例如：

```text
Cloudflare 账号
 ├── 负责人：time
 ├── 所属项目：个人网站
 ├── 关联资源：example.com 域名、CDN、DNS
 └── 轮换任务：2027-03-01 轮换 API Token
```

思源数据库的关联字段用于连接其他数据库或同一数据库中的条目；社区实践也常把它用于项目、概念、资源等对象之间的结构化关系。[^8_2][^8_1]

## 具体关联设计

| 账号库字段 | 关联目标 | 关系含义 | 使用价值 |
| :-- | :-- | :-- | :-- |
| 负责人 | 人员库 | 该账号由谁管理 | 离职、交接、权限审计 |
| 所属项目 | 项目库 | 账号服务于哪些项目 | 项目下线时检查关联账号 |
| 关联资源 | 资源库 | 账号可管理哪些域名、服务器、数据库 | 排查影响范围 |
| 轮换任务 | 任务库 | 为该账号创建的轮换 / 审计任务 | 到期前自动进入待办 |
| 备用联系人 | 人员库 | 紧急联系或二次负责人 | 降低单点依赖 |
| 关联文档 | 文档 / 笔记 | 配置说明、开通流程、故障处理 | 快速定位操作手册 |

其中“账号 ↔ 项目”“账号 ↔ 资源”建议使用双向关联：在项目里能看到它使用的账号，在账号里也能看到它影响的项目和资源。关联字段本质上是在不同数据库条目之间建立可复用的关系；双向关联可让两侧都能查看和编辑对应关系。[^8_3][^8_2]

## 账号生命周期示例

### 1. 新增账号

在“账号库”添加：

```text
服务名称：Vercel
用途：部署
环境：生产
状态：使用中
负责人：time
所属项目：个人网站
关联资源：blog 前端、API 服务
```

然后在“资源库”的 `blog 前端` 条目中，通过反向关联直接看到它依赖的 Vercel 账号。

### 2. 密钥轮换

在“任务库”添加：

```text
任务名：轮换 Vercel API Token
状态：todo
截止日期：2027-03-01
关联账号：Vercel
```

账号库中的“轮换任务”字段会显示该任务；到期前你可以在任务库按日期排序，或按“状态 = todo”筛选所有待处理轮换事项。

### 3. 项目下线

关闭“个人网站”项目前，打开该项目条目，查看反向关联的账号和资源：

```text
个人网站
 ├── 账号：Vercel、Cloudflare、Resend
 ├── 资源：域名、CDN、邮件 API、数据库
 └── 任务：删除 DNS、撤销 Token、导出数据
```

再为每个需要处理的账号创建“停用 / 删除 / 转移”任务，避免遗留可访问生产资源的凭据。

### 4. 人员交接

如果 `time` 不再负责某类服务，打开“人员库”中 `time` 的条目，通过反向关联查看其名下账号；再逐项修改“负责人”或创建交接任务。

## 与密码管理器配合

思源关联字段不应指向“密码”，而应指向**密码管理器条目的引用或编号**。


| 思源字段 | 内容示例 | 是否敏感 |
| :-- | :-- | :-- |
| 密码管理器条目 | `Bitwarden / Vercel / 生产账号` | 低，建议用内部编号或链接 |
| API Key | 不填写 | — |
| Secret | 不填写 | — |
| 恢复码 | 不填写 | — |
| 轮换策略 | `每 180 天` | 低 |
| 最后轮换日期 | `2026-10-01` | 低 |

这样，思源数据库回答“这个账号属于什么、影响什么、何时要处理”；密码管理器回答“凭据是什么、如何安全填充”。这是账号管理中更安全的职责分离。[^8_4][^8_5]

## 视图建议

在“账号库”中建立几个视图：


| 视图 | 分组 / 筛选 | 用途 |
| :-- | :-- | :-- |
| 全部账号 | 按服务或用途分组 | 资产总览 |
| 生产账号 | `环境 = 生产` | 高风险资产审查 |
| 待轮换 | `状态 = 待轮换` 或按到期日期排序 | 密钥治理 |
| 项目视角 | 按所属项目分组 | 项目下线、交接 |
| 负责人视角 | 按负责人分组 | 权限和责任分配 |

数据库的表格视图适合总览和筛选，看板适合按状态推进轮换、停用、交接等流程。[^8_6][^8_7]

## 注意事项

- **不要用关联字段存秘密**：关联字段连接的是数据库条目，不是加密保险库；凭据本体仍应放在密码管理器。
- **避免过度关联**：如果某个字段只是偶尔参考，用链接或文本即可；只有需要反复筛选、反向查看或批量管理时才建关联。
- **统一主键**：账号、资源、项目条目的名称要稳定，例如 `Vercel / 生产 / 个人网站`，否则后续维护容易混乱。
- **注意发布和共享范围**：思源数据库的关联定义、字段名等结构信息也可能在发布场景中暴露；涉及账号治理的库应避免发布到公开分享页面。[^8_8]

一句话：**用关联字段把“账号”变成账号资产网络的中心节点**——向上连项目和负责人，向下连资源和任务；但密码、Token、恢复码始终只放在密码管理器中。[^8_1][^8_2]

# 思源笔记中数据库（属性视图）为什么设计为使用独立的存储文件，而不是与其底层的SQL数据库表融合？

思源把数据库（属性视图）设计为独立的 `.av` 存储文件，而不是直接融合进底层 SQLite，主要是为了保持**文档树的可同步性、数据库的生命周期独立性、结构演进灵活性，以及 SQLite 作为查询索引而非唯一事实来源的定位**。属性视图自身是带版本、字段、值和多种视图定义的结构化对象，适合按 `avID` 独立持久化。[^9_1][^9_2][^9_3]

## 思源的存储分层

思源采用的是“文件为主、SQLite 为索引”的混合模型：


| 层 | 存储 | 作用 |
| :-- | :-- | :-- |
| 笔记内容 | `.sy` JSON 文件 | 保存文档块树，是可同步、可导出的内容源 [^9_3][^9_4] |
| 查询索引 | SQLite | 从 `.sy` 等数据重建索引，支持搜索和 SQL 查询 [^9_3] |
| 数据库 | 独立属性视图文件 | 按 `avID` 保存字段、值、视图、筛选等数据库结构 [^9_1][^9_2] |
| 资源 | `assets/` 文件 | 保存图片、附件、媒体文件 [^9_3] |

也就是说，SQLite 更像“为了快速查询而维护的索引/镜像”，而不是所有数据的唯一权威存储；`.sy` 与属性视图文件才是更基础的数据载体。[^9_3]

## 为什么不直接融合进 SQLite

### 1. 保持文档与同步模型一致

思源的核心同步单位是文档树和块，而不是关系型表。`.sy` 文件按文档组织，便于按文档、笔记本进行同步、历史版本管理和导出。如果把数据库数据全部写入全局 SQLite，就需要额外解决“哪台设备拥有哪张表、如何合并字段定义、如何处理并发写入”等分布式数据库同步问题。[^9_4][^9_3]

独立 `.av` 文件让一个数据库有清晰的 `avID` 和独立生命周期：创建、引用、删除、同步都可以围绕这个 ID 进行，而不必把数据库状态硬塞进文档同步协议。[^9_2][^9_1]

### 2. 数据库不是普通块内容

普通块的内容可以自然放进 `.sy` 的块树；但数据库包含：

- 字段定义：名称、类型、图标、排序；
- 单元格值：文本、数字、日期、选项、资源、关联等；
- 多个视图：表格、看板、画廊及其筛选、排序、分组、隐藏列；
- 条目与块的绑定关系；
- 格式版本 `Spec`。[^9_5][^9_1]

这些是“结构化数据 + 视图配置”的复合对象。独立文件使属性视图可以按自己的 schema 和版本演进，而不必被迫把复杂 JSON 塞进 SQLite 的固定表结构，或频繁做 schema migration。[^9_6][^9_1]

### 3. SQLite 的角色是查询索引

思源的 SQLite 主要用于把笔记内容映射为可 SQL 查询的关系型数据，例如 `blocks`、`attributes` 等表；它从源数据重建索引，异步更新以避免阻塞界面。[^9_3]

如果属性视图完全融合进 SQLite，会出现两个问题：

- **事实来源变模糊**：SQLite 既要当索引，又要当数据库主存储，崩溃恢复、重建索引、同步冲突时更难判断哪边是权威数据。
- **索引重建代价变高**：思源可以在内容变化后重建或更新索引；若数据库本体也在其中，重建索引就不能简单视为“可再生的派生数据”。[^9_3]


### 4. 便于按数据库粒度读写和备份

一个 `.av` 文件对应一个属性视图。读取某个数据库时，内核可以按 `avID` 直接定位并解析对应文件，而不必在全局 SQLite 中扫描、连接多张表。官方属性视图结构也显示，`AttributeView` 本身包含 `ID`、`Spec`、字段键值、视图列表等完整信息。[^9_1][^9_2]

这带来几个工程好处：

- 数据库创建、删除、复制更干净；
- 某个数据库损坏时，影响范围更容易隔离；
- 备份、迁移、调试时可以按数据库文件定位；
- 插件和 API 可以围绕 `avID` 做明确的读写边界。[^9_7][^9_1]


### 5. 支持数据库与文档松耦合

一个数据库可以被一个或多个数据库块引用；数据库块在 `.sy` 中主要保存 `avID`、当前视图等引用信息，而完整数据在属性视图文件中。[^9_8][^9_1]

这种设计让“数据”和“展示位置”解耦：

```text
属性视图文件（.av）
 └── avID: 20260101120000-xxxx
      ├── 字段、条目、视图
      └── 可被多个文档中的数据库块引用

文档 A (.sy)
 └── 数据库块 → avID

文档 B (.sy)
 └── 数据库块 → 同一个 avID
```

如果融合进 SQLite，也能实现引用，但“文件即数据、ID 即资源”的模型会更难与思源现有的文档同步、导出和块引用体系保持一致。[^9_2][^9_8]

## 这不是“SQL 不适合”

SQLite 本身完全能存结构化数据；问题不在于能力，而在于**职责划分**：


| 设计选择 | 若融合进 SQLite | 现行独立 `.av` 文件 |
| :-- | :-- | :-- |
| 主数据源 | SQLite 成为内容与数据库的共同主存储 | `.sy` 和 `.av` 为源数据，SQLite 为查询索引 [^9_3] |
| 同步粒度 | 需要数据库级、行级、字段级同步协议 | 可沿用文件 / 文档 / 资源粒度，数据库按 `avID` 管理 [^9_1][^9_3] |
| 结构演进 | 字段、视图变化需频繁迁移 SQL schema | 属性视图 JSON 可通过 `Spec` 版本演进 [^9_1] |
| 查询 | 查询和存储耦合 | SQL 查询索引与数据库主存储分离 [^9_3] |
| 故障恢复 | 索引损坏可能影响主数据 | 索引可重建，主数据边界更清晰 [^9_3] |

## 带来的取舍

这种设计也有代价：

- **跨数据库 SQL 关联不如传统关系库直接**：属性视图数据不在统一的 SQLite 表结构中，复杂跨库 JOIN、外键约束和事务语义不如真正的关系数据库。
- **API 更复杂**：操作数据库需要区分 `avID`、字段 `keyID`、行 `itemID`、块 `blockID` 等不同 ID 层级。[^9_7]
- **一致性依赖应用层**：块与数据库条目的绑定、字段值的有效性等，需要属性视图引擎维护，而不是完全交给数据库外键和约束。[^9_6][^9_1]


## 一句话理解

思源没有把属性视图塞进 SQLite，是因为它把 SQLite定位为**查询索引层**，而把 `.sy` 和 `.av` 作为**可同步、可迁移、可独立演进的源数据层**；数据库需要自己的字段、视图、版本和生命周期，独立文件能让它既融入笔记系统，又不破坏文档同步与索引重建的架构边界。[^9_1][^9_2][^9_3]

# 当前思源笔记的块属性和数据库设计及功能存在哪些短板和用户使用痛点？

当前思源的块属性和数据库已经能覆盖轻量标记、任务管理和结构化知识库，但在**属性体系统一、编辑体验、查询能力、关联/汇总深度、行与文档绑定、性能和自动化**上仍有明显短板。官方 Issue 也集中反映了这些痛点。[^10_1][^10_2][^10_3][^10_4]

## 属性体系：概念多但不够统一

思源目前同时存在内置属性、自定义块属性、数据库字段、标签、书签等多种元数据机制。用户很难判断“状态”应该写成块属性、标签，还是数据库字段；同一概念在不同数据库中也可能重复定义、类型不同、选项不同。[^10_3][^10_5]


| 痛点 | 表现 | 影响 |
| :-- | :-- | :-- |
| 缺少全局属性 | `status`、`priority` 等无法在工作空间统一定义和复用 | 同名属性易拼写不一致，选项和类型难以统一 [^10_3] |
| 块属性是弱类型字符串 | `priority=3`、`high`、`高` 都能写入 | 查询、筛选和自动化前需要额外清洗 [^10_5] |
| 属性面板入口较深 | 主要通过块标菜单查看、编辑 | 高频维护时操作繁琐 [^10_1] |
| 数据库属性展示不直观 | 块或文档的数据库属性在编辑器中展示方式有限 | 用户难以在写作时直接看到和修改上下文属性 [^10_6][^10_7] |
| 搜索不完整 | 难以直接按“所属数据库 + 数据库属性”定位块 | 数据库难以完全替代标签或轻量数据库查询 [^10_2] |

社区已提出“全局属性”需求，希望多个数据库共用同一属性定义和属性值，甚至让属性本身成为可复用的关系对象；这说明当前分散式属性设计确实是核心痛点。[^10_3]

## 数据库：结构化能力仍有缺口

### 1. SQL 与数据库尚未打通

思源的 SQL 查询主要面向块索引，而属性视图数据保存在独立结构中；用户想用 SQL 直接查询数据库字段、跨库关联或聚合时，体验不完整。有 Issue 指出，通过 API 获取块的数据库属性时，块数量较多会产生多次请求，效率不佳。[^10_8]

这导致一个常见矛盾：**数据库适合管理结构化数据，但 SQL 适合查询块；两者没有形成统一的查询层。**[^10_9][^10_8]

### 2. 关联与汇总能力偏基础

关联字段可以连接数据库条目，但候选过滤主要依赖关键字，难以直接按关联目标的其他字段元信息筛选；这会让大型数据库中的关联选择变得低效。[^10_10]

汇总能力也有局限。例如，多个关联列分别指向不同数据库时，想对它们的结果统一求和或做其他统计，当前模板方式难以实现或过于繁琐；官方近期改进了关联字段的主键显示模板，但多关联列汇总仍未纳入。[^10_11]


| 场景 | 期望 | 当前痛点 |
| :-- | :-- | :-- |
| 选择关联对象 | 按状态、项目、负责人等字段过滤候选 | 主要靠关键字匹配，元信息难以参与筛选 [^10_10] |
| 多表汇总 | 汇总多个关联列的数据 | 多关联列汇总支持不足 [^10_11] |
| 跨库分析 | SQL 直接 JOIN 属性视图数据 | SQL 与属性视图查询未完全统一 [^10_8] |
| 复杂视图 | 灵活分组、筛选、排序、汇总 | 分组、模板求值等仍有边界和性能问题 [^10_12][^10_13] |

### 3. 行与文档的绑定模型不灵活

思源数据库条目常与块绑定，这带来知识管理和双向链接的优势，但也造成“轻量数据”场景的负担：新建数据库行时可能生成文档块，进而产生大量小文件。有用户以背单词为例：成百上千个单词会对应大量几乎为空的文档文件。[^10_4]

官方讨论中也承认，数据库行可以不绑定块；但当前模型下，行、块、文档三者的关系仍会让用户困惑，尤其在移动、删除、归档数据库或文档时，容易出现预期不一致。[^10_14][^10_15]


| 用户目标 | 当前摩擦 |
| :-- | :-- |
| 建一个纯数据表，如单词、库存、联系人 | 新建行可能创建文档，产生文件膨胀 [^10_4] |
| 把数据库行当作轻量记录 | 行与块/文档的绑定策略不够灵活 [^10_14][^10_15] |
| 移动或整理数据库 | 关联文档的位置和随动行为曾存在边界问题 [^10_15] |
| 像 Notion 一样“打开才创建页面” | 缺少更自然的懒创建 / 非绑定行策略 [^10_15] |

## 编辑与视图体验

### 1. 属性编辑路径较长

块属性主要通过块标菜单进入，文档级属性和数据库属性的编辑入口也不完全一致。用户希望属性面板可浮动、可在文档顶部集中管理，或聚焦块时直接显示相关数据库属性。[^10_6][^10_1]

对高频使用者来说，这会降低“边写边打标”的效率；属性本应是轻量元数据，但当前操作成本偏高。[^10_7][^10_1]

### 2. 多视图一致性不足

数据库支持表格、看板、画廊等视图，但不同视图之间的字段添加、排序和展示逻辑并不总是完全一致。例如，在一个布局中添加字段时，未必同步出现在其他布局；画廊视图的字段排序逻辑也曾被集中反馈。[^10_16]

这会让用户在维护“同一数据库的多个视图”时，需要反复检查字段是否遗漏、排序是否符合预期。[^10_16]

### 3. 模板字段与筛选、排序的配合有限

模板字段的求值与过滤、排序、分组、汇总之间存在依赖问题：当这些操作依赖模板结果时，需要提前求值；否则被过滤或分页挡住的条目也可能执行模板，带来正确性和性能权衡。[^10_13]

对普通用户而言，结果是：模板字段适合展示，但把它当作可靠的计算列、筛选条件或排序依据时，心智负担较高。[^10_13]

## 性能与规模化

随着数据库条目、视图、分组和关联增多，性能会成为痛点。官方已有议题讨论改进编辑、数据库视图和搜索性能，涉及文档动态加载、视图虚拟滚动、按块哈希跳过未变块索引更新等方向；这也侧面说明大库、多视图和频繁编辑场景仍有优化空间。[^10_17]


| 规模化场景 | 潜在痛点 |
| :-- | :-- |
| 数千行任务或词条 | 新建行生成文档导致文件数量膨胀 [^10_4] |
| 多个复杂视图 | 分组、虚拟滚动和视图渲染需要持续优化 [^10_17][^10_12] |
| 大量关联字段 | 关联候选、显示和汇总的计算成本上升 [^10_10][^10_11] |
| SQL 查询数据库属性 | 需要多次 API 请求或缺乏统一查询路径 [^10_8] |

## 自动化与 API

思源已有属性视图 API，但自动化仍偏开发者向：需要区分 `avID`、字段 `keyID`、行 `itemID`、块 `blockID` 等不同 ID；社区也在请求更简化的数据库维护接口，例如按文档名称和数据库 ID 新增记录。[^10_18][^10_19]

对普通用户来说，这意味着“自动把带某块属性的块收进数据库”“批量同步字段”“跨库同步状态”等需求，往往要依赖插件、RunJS、Quicker 或外部脚本，而不是原生规则。[^10_19][^10_18]

## 最影响日常使用的短板

如果按影响排序，当前最值得关注的痛点是：

1. **缺少全局属性**：属性定义分散，跨库复用和一致性差。[^10_3]
2. **块属性编辑和展示不够顺手**：高频打标、查看上下文属性的成本高。[^10_1][^10_6]
3. **SQL 与数据库查询未统一**：难以用一套查询语言同时查块、属性和数据库字段。[^10_8]
4. **关联候选过滤和汇总能力不足**：复杂项目、资源、账号管理场景受限。[^10_10][^10_11]
5. **行与文档绑定策略不灵活**：轻量数据表容易产生大量小文档。[^10_15][^10_4]
6. **自动化依赖插件和 API**：原生缺少低门槛的收集、同步和批量维护规则。[^10_18][^10_19]

## 对使用策略的影响

在短板补齐前，比较稳妥的使用原则是：

- **轻量标记用块属性或标签**，不要把所有元数据都塞进数据库。
- **需要看板、日期、关联、汇总时才建数据库**，避免把普通文档强行表格化。
- **同一概念跨多个数据库使用时，先制定命名和取值规范**，例如 `custom-status = todo/doing/done`，减少未来迁移成本。[^10_3]
- **复杂查询暂用 SQL 查块、数据库视图查条目**，不要期望二者已经完全等价。[^10_8]
- **批量收集、同步、轮换提醒等自动化**，优先用插件或 API，并把脚本设计成幂等操作。[^10_19][^10_18]

一句话：思源的块属性和数据库方向是对的——**块级知识 + 结构化数据**；但当前主要卡在“属性定义分散、块与数据库查询割裂、关联汇总不够深、行文档绑定不够灵活、自动化门槛偏高”。[^10_4][^10_1][^10_8][^10_3]

# 对比Notion思源的数据库差距在哪里

Notion 的数据库在**产品成熟度、关系建模、公式与汇总、协作权限、自动化和生态**上明显领先；思源的优势则在于**本地数据所有权、块级知识管理、SQL 查询、开源可自托管和隐私控制**。若把数据库当作轻量项目/知识管理工具，思源已够用；若要构建复杂业务系统或多团队协作工作台，Notion 仍更完整。[^11_1][^11_2][^11_3]

## 总体定位差异

| 维度 | Notion | 思源笔记 |
| :-- | :-- | :-- |
| 产品重心 | All-in-one 工作区：文档、数据库、协作、自动化 | 本地优先、块级知识管理 + 结构化数据 [^11_2][^11_3] |
| 数据库定位 | 页面集合 + 多视图工作台，接近轻量业务系统 | 属性视图：块与结构化数据的结合 [^11_1][^11_2] |
| 部署与数据 | 云端为主，企业能力较完整 | 开源、可自托管、数据本地可控 [^11_3] |
| 协作 | 多人实时协作、权限、分享、集成生态较强 | 更偏个人 / 小团队知识库，协作能力相对弱 [^11_2][^11_3] |
| 扩展方式 | 官方集成、API、自动化、模板生态 | 插件、API、SQL、本地脚本，灵活但门槛更高 [^11_4][^11_3] |

## 数据模型差距

### 1. 关系与汇总

Notion 的关系和汇总是数据库的核心能力：Relation 连接两个数据库，Rollup 可沿关系读取关联页属性，并执行计数、求和、平均值、最新日期等计算；表格和看板还能对 Rollup 列做整体统计。[^11_5][^11_1]

思源也有关联字段，但汇总和跨库计算能力较弱；关联候选筛选主要依赖关键字，难以充分按关联对象的其他字段过滤；多关联列汇总等复杂场景也存在限制。[^11_6][^11_7]


| 能力 | Notion | 思源 |
| :-- | :-- | :-- |
| 跨库关联 | 成熟，支持单向 / 双向关系 [^11_1] | 支持关联，但产品化程度较低 [^11_6] |
| 关联候选筛选 | 可结合数据库属性和视图能力选择关联对象 | 主要靠关键字，元信息筛选不足 [^11_6] |
| Rollup 汇总 | 内置，支持计数、求和、平均、日期等 [^11_1][^11_5] | 汇总能力有限，复杂跨库汇总不足 [^11_7] |
| 关系可视化 | 页面、数据库和关系图较完整 | 关系图对数据库关联字段的支持仍在演进 [^11_8] |
| 复杂业务建模 | 更适合 CRM、项目组合、内容日历等 | 更适合个人知识库和轻量资产台账 [^11_2][^11_9] |

### 2. 公式与派生字段

Notion 的 Formula 可基于当前页属性计算派生值，例如剩余天数、逾期标记、状态图标、文本拼接；公式还能结合 Rollup 结果，形成“关系 → 汇总 → 公式”的建模链路。[^11_10][^11_11][^11_12]

思源有模板字段，但更接近模板求值和展示；在筛选、排序、分组、汇总依赖模板结果时，求值时机和性能仍有边界问题。[^11_13]


| 场景 | Notion | 思源 |
| :-- | :-- | :-- |
| `剩余天数 = 截止日期 - 今天` | Formula 原生支持 [^11_11] | 需模板字段或外部计算，能力与体验较弱 [^11_13] |
| `项目完成度 = 已完成任务 / 总任务` | Relation + Rollup + Formula 可组合 [^11_1][^11_12] | 难以低门槛实现 |
| 逾期自动标红 | 公式 + 视图条件较成熟 [^11_11] | 需手动维护或脚本辅助 |
| 模板字段作为筛选 / 排序依据 | 更稳定 | 存在求值与性能边界 [^11_13] |

## 视图与交互差距

Notion 的核心优势是“同一数据、多种工作视图”：表格、看板、日历、时间线、画廊、列表都只是同一数据库的不同窗口；视图的筛选、排序、分组和布局彼此独立，不会改变底层数据。[^11_9][^11_11][^11_12]

思源已有表格、看板、画廊等视图，但视图体系仍在完善：不同布局间的字段添加、排序逻辑曾存在不一致；分组、虚拟滚动和模板求值也有性能与体验问题。[^11_14][^11_15][^11_16]


| 视图能力 | Notion | 思源 |
| :-- | :-- | :-- |
| 表格 | 成熟 | 有，是默认视图 [^11_17] |
| 看板 | 成熟 | 有 [^11_18] |
| 日历 / 时间线 | 成熟，适合排期和项目计划 [^11_9][^11_11] | 日历等能力仍在演进 [^11_19] |
| 画廊 | 成熟 | 有，但多视图字段与排序一致性曾有反馈 [^11_14] |
| 链接视图 | 可在任意页面嵌入同一数据库的独立视图 [^11_9] | 可嵌入数据库块，但视图复用与配置灵活度较弱 |
| 视图配置独立性 | 视图筛选、排序、分组不影响源数据 [^11_12] | 基本可用，但复杂视图一致性仍需完善 [^11_14][^11_16] |

## 协作与权限差距

Notion 的数据库天然面向团队：页面级权限、数据库共享、集成访问控制、评论、多人实时编辑和自动化都更完整；其 API 也要求连接先获得数据库共享权限才能查询。[^11_4]

思源更适合个人或小团队的本地知识库。它支持多设备同步和协作方向，但数据库级别的细粒度权限、审批流、外部用户访问、企业级治理不如 Notion 成熟。[^11_2][^11_3]


| 场景 | 更适合 |
| :-- | :-- |
| 个人笔记、研究资料、本地知识库 | 思源 [^11_3] |
| 团队 Wiki、项目看板、CRM | Notion [^11_1][^11_2] |
| 需要给外部协作者分配细粒度权限 | Notion [^11_4] |
| 需要数据完全本地化、可自托管 | 思源 [^11_3] |
| 需要低代码搭建团队工作台 | Notion [^11_1][^11_9] |

## 自动化与生态差距

Notion 有较完整的官方集成、API、自动化、模板市场和第三方工具生态；数据库查询 API 也明确支持外部连接在获得授权后查询数据库。[^11_4][^11_9]

思源的自动化更依赖插件、RunJS、Quicker、HTTP API 和本地脚本。它的优势是可自托管、可深度定制；劣势是需要用户具备开发能力，且缺少 Notion 那类低代码自动化和庞大 SaaS 集成生态。[^11_3][^11_20][^11_21]


| 能力 | Notion | 思源 |
| :-- | :-- | :-- |
| 官方自动化 | 较完整 | 主要靠插件 / 脚本 [^11_20][^11_21] |
| 第三方集成 | 丰富 | 相对有限 |
| API | 文档和权限模型较成熟 [^11_4] | 可用，但 ID 层级和接口较复杂 [^11_21] |
| 模板市场 | 生态大 | 社区模板和插件生态较小 |
| 自定义开发 | 受平台限制 | 开源、可自托管、可深度改造 [^11_3] |

## 思源独有的优势

思源并非全面落后；在以下方面它反而更适合特定用户：


| 优势 | 说明 |
| :-- | :-- |
| 本地优先与数据所有权 | 工作空间数据可保存在本地，支持自托管，降低平台锁定风险 [^11_3] |
| 块级知识管理 | 每个块都有稳定 ID，块引用、反链和 SQL 查询与知识管理结合更紧密 [^11_2] |
| SQL 查询 | 可以直接查询块索引，适合技术型用户做高级检索 [^11_2] |
| 开源与可扩展 | 可自托管、可审查、可按需求改造 [^11_3] |
| 隐私控制 | 更适合不想把全部笔记和结构化数据交给云端 SaaS 的用户 [^11_3] |

## 选型判断

| 你的需求 | 推荐 |
| :-- | :-- |
| 个人知识库、文献管理、本地优先、块级双链 | 思源 |
| 需要开源、自托管、避免按席位付费 | 思源 [^11_3] |
| 需要复杂 Relation / Rollup / Formula 建模 | Notion [^11_1][^11_11] |
| 团队协作、权限、审批、外部共享 | Notion [^11_4][^11_2] |
| CRM、项目组合、内容日历、多团队工作台 | Notion [^11_2][^11_9] |
| 技术型用户想用 SQL、脚本和本地数据构建系统 | 思源 [^11_2][^11_3] |
| 需要丰富 SaaS 集成和低代码自动化 | Notion [^11_4][^11_9] |

一句话：**Notion 数据库更像“可协作的低代码业务工作台”，思源属性视图更像“嵌在本地知识库中的结构化数据层”**。Notion 赢在关系、汇总、公式、协作和生态；思源赢在数据主权、块级知识管理、SQL 和可自托管。[^11_1][^11_2][^11_3]

# 对比一下两种使用方式：1. 先各自配置块属性，然后聚合成数据库；2. 构建数据库，将相关块设为主键；这两种方式各适用于什么场景，分别解决什么痛点，有什么建议？

这两种方式代表两条相反的数据建模路径：**方式 1 是“先写块、后聚合”**，适合知识沉淀和渐进式收集；**方式 2 是“先建表、再挂块”**，适合任务、项目、资产等需要稳定字段和流程管理的对象。思源中前者更接近“块属性 + 收集/查询”，后者更接近“数据库主键块 + 字段管理”。[^12_1][^12_2]

## 两种模式对比

| 维度 | 方式 1：块属性 → 聚合成数据库 | 方式 2：数据库 → 块作为主键 |
| :-- | :-- | :-- |
| 起点先有 | 内容块 | 数据库 schema |
| 数据归属感 | 内容优先，属性是补充 | 记录优先，块是记录载体 |
| 字段定义 | 分散在各个块属性中 | 集中在数据库字段中 |
| 类型能力 | 弱，基本是字符串键值对 | 强，有文本、数字、日期、单选、多选、关联等 [^12_2] |
| 入库方式 | 后续筛选、收集或脚本同步 | 创建时即成为数据库条目 |
| 适合数据量 | 少量、渐进积累 | 中大量、持续维护 |
| 主要痛点 | 命名不一致、类型不一致、聚合成本 | 前期设计成本、行与文档绑定、结构僵化 [^12_1][^12_3] |
| 典型场景 | 文献摘录、灵感、会议纪要、技术笔记 | 任务库、项目库、工具库、账号台账 |

## 方式 1：先配置块属性，再聚合

### 工作流

```text
写笔记 / 摘录 / 会议记录
        ↓
给相关块加 custom-status、custom-topic、#tag#
        ↓
用 SQL、嵌入块或收集规则找到这些块
        ↓
聚合成数据库 / 生成任务 / 建立索引
```

例如，你在阅读技术文章时随手记录：

```text
这段讲 PTY 与 shell 的关系。 #terminal #ai-agent
custom-topic=terminal
custom-importance=high
```

之后用查询块筛选所有 `custom-topic=terminal` 且 `custom-importance=high` 的块，或把它们收进“技术灵感库”。

### 解决什么痛点

- **不打断写作**：先记录内容，稍后再决定是否结构化。
- **避免过早建模**：不必一开始就设计“灵感库”“文献库”的字段。
- **保留上下文**：块属性挂在原始内容上，后续聚合时仍能回溯原文。
- **适合异构内容**：同一条 `custom-topic=ai-agent` 可以同时标记摘录、命令、代码块、会议结论。


### 适用场景

| 场景 | 为什么适合 |
| :-- | :-- |
| 文献阅读与摘录 | 摘录先产生，主题、评分、是否复习后补 |
| 灵感与素材收集 | 先捕捉，再按主题、优先级聚合 |
| 会议纪要 | 先记录决议和行动项，再提取为任务 |
| 技术笔记 | 给命令、配置、坑点打属性，后续形成检索入口 |
| 零散任务 | 在任意笔记里写“TODO”，后续统一收进任务库 |

### 主要风险

1. **属性命名漂移**：今天写 `custom-status`，明天写 `custom-state`；后续聚合时会查不全。
2. **取值不规范**：`high`、`高`、`P1` 混用，导致筛选失败。
3. **聚合滞后**：块属性只是候选数据，若没有定期收集或同步，数据库不会自动拥有这些记录。
4. **弱类型限制**：日期、数字、多选等需要额外解析，不能直接获得数据库字段能力。[^12_2]

## 方式 2：先建数据库，块作为主键

### 工作流

```text
设计数据库：任务库 / 项目库 / 工具库
        ↓
定义字段：状态、优先级、负责人、截止日期、所属项目
        ↓
新建条目，选择或创建主键块
        ↓
在数据库中维护字段、视图、关联和汇总
```

例如“开发任务库”：

```text
主键块：完成数据库同步插件
状态：doing
优先级：high
负责人：time
截止日期：2026-11-01
所属项目：思源工具链
```

主键块是这条记录在笔记中的锚点；数据库字段则承载结构化管理信息。思源的属性视图本身就以字段和条目组织数据，条目可以绑定块，这使数据库记录能自然嵌入文档和双链体系。[^12_3][^12_1]

### 解决什么痛点

- **字段类型可靠**：状态、日期、数字、选项有明确类型，便于筛选、排序和看板。
- **流程可管理**：任务从 `todo → doing → done` 可以用看板和筛选持续跟踪。
- **关系清晰**：任务可关联项目、负责人、资源，形成结构化网络。
- **视图复用**：同一批记录可按表格总览、按状态看板、按日期排期。
- **减少事后整理**：数据在创建时就进入统一 schema，不需要后期批量清洗。


### 适用场景

| 场景 | 为什么适合 |
| :-- | :-- |
| 任务与项目管理 | 有状态、负责人、截止日期，需要看板和筛选 |
| 项目组合管理 | 项目、任务、资源之间需要关联 |
| 工具 / 账号资产库 | 需要许可证、到期时间、负责人、关联资源等稳定字段 |
| 内容选题库 | 需要选题状态、发布日期、平台、素材链接 |
| 人脉 / 会议库 | 需要按人员、组织、时间、后续行动管理 |

### 主要风险

1. **过早设计 schema**：字段设计不当后，迁移和补录成本高。
2. **结构僵化**：所有内容被迫适应表格字段，可能损失写作自由度。
3. **行与文档绑定负担**：如果每条记录都创建文档，轻量数据可能产生大量小文件；官方讨论中已指出数据库行可以不绑定块，但当前模型仍容易让用户困惑。[^12_1][^12_3]
4. **维护成本前置**：需要先想清楚主键、字段、视图、关联，否则数据库会变成“半成品表格”。

## 如何选择

### 用方式 1，当满足这些条件

- 内容先于结构出现；
- 记录数量不确定，或初期不想设计字段；
- 同一属性要标记异构内容；
- 后续才决定哪些内容值得进入数据库；
- 你能接受后期用 SQL、插件或脚本做聚合。


### 用方式 2，当满足这些条件

- 对象有稳定生命周期，例如任务、项目、账号、工具；
- 需要固定字段，例如状态、日期、负责人、优先级；
- 需要看板、筛选、排序、关联或汇总；
- 数据会持续增加，且需要多人或跨文档追踪；
- 你愿意先做一点 schema 设计。


## 推荐的混合模式

实际中最有效的是\*\*“方式 1 捕捉，方式 2 治理”\*\*：

```text
捕捉层：块属性 / 标签
  custom-capture=true
  custom-topic=ai-agent
  custom-priority=high

聚合层：定期检查 / SQL / 插件
  找到候选块

治理层：数据库
  任务库、项目库、文献库
  字段、状态、关联、视图
```

建议规则：

1. **捕捉属性保持极少**：只放 `capture`、`topic`、`priority` 这类必要字段，避免把数据库字段全部复制到块属性。
2. **数据库承载正式状态**：一旦内容被确认为任务、项目或资产，就进入数据库，由数据库字段管理后续状态。
3. **主键块保持简洁**：主键块放标题和核心描述，详细内容放正文、子文档或关联文档。
4. **统一命名规范**：例如 `custom-status`、`custom-topic`、`custom-priority`；取值使用固定英文枚举，减少聚合失败。[^12_2]
5. **区分“候选”与“正式记录”**：块属性表示“可能要进入某个库”，数据库字段表示“已经是受管理的记录”。
6. **避免双向重复维护**：块属性用于入库条件；入库后，状态、日期、负责人等应以数据库字段为准，不要同时手工维护两份。

## 一个实际例子

管理开发任务时：

- **捕捉阶段**：在每日笔记里写：

```text
- 需要研究思源数据库 API 的批量写入限制 #task
  custom-capture=task
  custom-topic=siyuan
```

- **聚合阶段**：用查询或插件找到 `custom-capture=task` 且未入库的块。
- **治理阶段**：确认后加入“开发任务库”：

```text
任务名：研究思源数据库 API 的批量写入限制
状态：todo
优先级：medium
所属项目：思源工具链
截止日期：2026-11-05
```

这样，块属性负责**低成本捕捉**，数据库负责**高可靠管理**；既不会为了记一条灵感先建表，也不会让任务长期散落在普通笔记里。[^12_3][^12_1][^12_2]

# 有没有插件或自动化脚本能降低块聚合的成本

有，而且现在**思源原生已支持数据库自动化收集**：可以按标签、自定义块属性、笔记本/文档、块类型等条件，把匹配块自动收进数据库，并通过模板给字段赋值。这比过去只能靠插件或脚本的方式成本低得多。[^13_1][^13_2]

## 原生方案：数据库自动化收集

思源较新版本的数据库支持自动化规则：

- 按**标签**、**自定义属性**、笔记本、文档、块类型等条件选择来源块；
- 将匹配块收集为数据库条目；
- 使用模板为数据库字段赋值；
- 支持属性名的子串和正则匹配；
- 自动收集只新增条目，重复匹配会保持同一行和已有字段值，避免重复创建。[^13_2][^13_1]

官方 API 文档描述了 `block` 触发器：`blockSource` 可选择笔记本、文档、块类型、标签和自定义属性；`collect` 动作会把匹配的来源块绑定到数据库。标签与属性条件默认是 AND，也可在组内配置 OR。[^13_2]

### 适合的规则示例

| 目标 | 自动化条件 | 建议字段赋值 |
| :-- | :-- | :-- |
| 收集所有任务块 | 标签包含 `#task#` | 状态默认 `todo` |
| 收集高优先级灵感 | `custom-capture=idea` 且 `custom-priority=high` | 类型 = 灵感 |
| 收集指定文档中的待办 | 笔记本 / 文档范围 + 列表项类型 | 来源文档作为关联或文本 |
| 收集带特定属性的块 | `custom-topic` 匹配 `siyuan` 或正则 | 主题 = SiYuan |
| 收集会议行动项 | 标签 `#action#` | 状态 = `todo`，截止日期留空待补 |

例如，你可以建一个“开发任务库”，配置规则：

```text
来源：指定笔记本 / 指定文档
块类型：列表项
标签：#task#
自定义属性：custom-priority = high
动作：收集到数据库
字段模板：状态 = todo
```

之后只要在任意符合条件的列表项上写 `#task#`，它就会被收进任务库；再次匹配时不会重复新增。[^13_1][^13_2]

## 插件方案

### 1. Database Properties Panel

`siyuan-database-properties-panel` 插件能在数据库行对应页面上**自动显示并编辑该行的数据库属性**。它不直接解决“收集”，但能显著降低“块 ↔ 数据库字段”的查看和编辑成本。[^13_3]

适合场景：

- 你已经把块收进数据库；
- 打开该块对应页面时，希望直接看到状态、优先级、截止日期等字段；
- 不想每次都回到数据库表格中修改。


### 2. 属性面板类插件

社区还有属性面板插件，用于在文档或块附近展示自定义属性；官方也曾讨论原生属性面板，但认为由于文档块和其他块都可加入数据库，统一设计较复杂，短期未计划原生实现。[^13_4]

这类插件适合“边写边打标”，但对数据库收集本身帮助有限。

## 自动化脚本方案

如果原生规则不能覆盖你的逻辑，可以用思源 Kernel API 写脚本。API 支持读取 / 设置块属性、执行 SQL、操作块和文档；自定义属性必须带 `custom-` 前缀。[^13_5][^13_6]

### 典型脚本流程

```text
1. SQL 查询候选块
   WHERE tag LIKE '%#task#%'
     AND custom-capture = 'task'

2. 检查是否已入库
   读取 custom-synced 或查询数据库条目

3. 调用属性视图 API
   将块加入目标 avID

4. 按字段类型写入值
   custom-priority=high → 优先级（单选）
   custom-due=2026-11-01 → 截止日期（日期）

5. 写回同步标记
   custom-synced=<avID>
   custom-synced-at=<timestamp>
```

思源 API 提供 `/api/attr/getBlockAttrs` 和 `/api/attr/setBlockAttrs`，可用于读取和写入 `custom-status`、`custom-priority` 等属性；插件开发环境也封装了 `getBlockAttrs`、`setBlockAttrs` 和 SQL 查询能力。[^13_6][^13_5]

### 最小伪代码

```js
const candidates = await sql(`
  SELECT id, content
  FROM blocks
  WHERE tag LIKE '%#task#%'
`);

for (const block of candidates) {
  const attrs = await getBlockAttrs(block.id);

  if (attrs["custom-synced"] === TARGET_AV_ID) continue;

  await addToDatabase({
    avID: TARGET_AV_ID,
    blockID: block.id,
    fields: {
      status: attrs["custom-status"] ?? "todo",
      priority: attrs["custom-priority"] ?? "medium"
    }
  });

  await setBlockAttrs(block.id, {
    "custom-synced": TARGET_AV_ID,
    "custom-synced-at": new Date().toISOString()
  });
}
```

关键点是**幂等**：先检查 `custom-synced`，或查询该块是否已是数据库条目，避免定时任务重复添加。[^13_5][^13_6]

## 外部自动化平台

如果希望跨应用自动化，可以使用 n8n 等工具。社区已有 SiYuan 的 n8n 节点，支持文档管理、块操作、读取 / 设置自定义属性、执行 SQL 等能力，可把思源与日历、邮件、任务服务、Webhook 等连接起来。[^13_7]

适合流程：

```text
思源新任务块
  → n8n 定时 / Webhook 触发
  → 查询块属性
  → 写入思源数据库
  → 同时创建日历提醒或通知
```


## 方案选择

| 需求 | 推荐方案 | 成本 |
| :-- | :-- | :-- |
| 按标签或块属性自动收进数据库 | 思源原生数据库自动化 | 最低 [^13_1][^13_2] |
| 收集时自动填字段 | 原生自动化 + 模板字段赋值 | 低 [^13_1] |
| 在块页面直接编辑数据库字段 | Database Properties Panel 插件 | 低 [^13_3] |
| 复杂筛选、跨库同步、幂等批量导入 | RunJS / 插件 / API 脚本 | 中 [^13_5][^13_6] |
| 跨应用流程，如日历、邮件、Webhook | n8n / 外部自动化 | 中高 [^13_7] |
| 只想临时查看匹配块 | SQL / 嵌入块查询 | 最低 [^13_8] |

## 实践建议

1. **优先用原生自动化**：只要条件能表达为标签、块属性、块类型、笔记本或文档范围，就不必写脚本。[^13_1][^13_2]
2. **规则保持单一职责**：一个规则只负责一类收集，例如“`#task#` → 任务库”“`#idea#` → 灵感库”，便于排查和停用。
3. **用固定枚举值**：`todo/doing/done`、`low/medium/high`，避免中文、英文、编号混用。
4. **入库后以数据库字段为准**：块属性只作为入选条件；后续状态、日期、负责人应维护在数据库中。
5. **脚本必须幂等**：使用 `custom-synced=<avID>` 或查询已有条目，防止定时任务重复收集。[^13_6][^13_5]
6. **先用预览验证**：自动化涉及批量写入，先小范围试运行，确认匹配范围和字段赋值无误后再扩大。[^13_2]

一句话：**现在降低聚合成本的首选是思源原生的数据库自动化收集**；插件适合改善属性编辑体验，API / n8n 则适合原生规则覆盖不了的跨库、跨应用或复杂幂等同步。[^13_3][^13_7][^13_1][^13_2]

# 当前思源笔记是如何在文档中显示数据库视图的，如何在文档中插入视图，是否允许多处插入同一视图，是否有自动展示机制？

思源在文档中显示数据库，本质是插入一个**数据库块（`NodeAttributeView`）**；该块只保存“指向哪个属性视图、当前显示哪个视图”的引用，真正的字段、条目和视图定义存放在独立的属性视图数据文件中。因此，**同一个数据库可以在多个文档、多个位置插入**，并且每个插入点可以记住不同的视图。[^14_1]

## 文档中的显示机制

一个数据库块在 `.sy` 文档中的核心结构是：

```json
{
  "Type": "NodeAttributeView",
  "ID": "数据库块ID",
  "Properties": {
    "custom-sy-av-view": "视图ID",
    "id": "数据库块ID",
    "updated": "..."
  },
  "AttributeViewID": "属性视图ID",
  "AttributeViewType": "table"
}
```

其中：

- `AttributeViewID`：指向实际数据库数据，即属性视图 `avID`；
- `custom-sy-av-view`：该数据库块当前显示的视图 ID；
- `AttributeViewType`：`table`、`kanban`、`gallery` 等布局类型的缓存值；
- 数据库块本身没有 `Children`，不直接保存表格数据。[^14_1]

所以文档里看到的不是“表格数据被复制进文档”，而是文档中的一个**数据库视图挂载点**。[^14_1]

## 如何在文档中插入

在文档中输入斜杠命令：

```text
/database
/sjk
/数据库
```

即可创建或插入数据库块。创建后，可通过数据库右上方的视图菜单添加、切换、编辑视图；每个视图可独立设置布局、筛选、排序、分组和显示字段。[^14_2]

也可以把已有内容块通过块标菜单的“添加到数据库”加入某个数据库；这会把块作为数据库条目绑定，而不是在当前位置插入整个数据库视图。[^14_3]

## 是否允许多处插入同一视图

**允许插入同一个数据库，但“同一视图”的复用方式要区分。**


| 情况 | 是否支持 | 行为 |
| :-- | :-- | :-- |
| 多个文档插入同一个数据库 | 支持 | 多个数据库块引用同一个 `AttributeViewID` [^14_1] |
| 多个位置显示同一数据库的不同视图 | 支持 | 每个数据库块用 `custom-sy-av-view` 记录自己的视图 [^14_1] |
| 多个位置显示完全相同的视图配置 | 支持 | 多个块可指向同一个 `avID + viewID` |
| 一个插入点独立修改筛选 / 排序 | 取决于是否使用同一视图 | 若共用同一 `viewID`，视图配置是共享的；若需要不同筛选，应创建不同视图 |

关键在于：`custom-sy-av-view` 是**数据库块级别**的视图选择器；它决定“这个插入点显示哪个视图”。但视图本身的筛选、排序、分组等配置保存在属性视图中，因此多个块指向同一个视图时，会共享该视图的配置。[^14_2][^14_1]

举例：

```text
任务库 avID: 20260101120000-task
 ├── 视图 A：全部任务
 ├── 视图 B：进行中
 └── 视图 C：本周截止

文档 A
 └── 数据库块 1 → avID + 视图 A

文档 B
 └── 数据库块 2 → avID + 视图 B

文档 C
 └── 数据库块 3 → avID + 视图 A
```

文档 A 和文档 C 显示的是同一个“全部任务”视图，因此它们的筛选、排序、字段显示配置是共享的；文档 B 显示“进行中”视图，配置独立。[^14_2][^14_1]

## 是否有自动展示机制

思源**没有通用的“文档自动根据上下文展示某个数据库视图”机制**；数据库块必须被显式插入到文档中，并显式或默认地选择一个视图。[^14_1]

不过有几种接近“自动展示”的方式：


| 机制 | 是否自动 | 说明 |
| :-- | :-- | :-- |
| 数据库块默认视图 | 半自动 | 若块未指定有效 `custom-sy-av-view`，或该视图已不存在，会回退到属性视图中的第一个可用视图。 [^14_1] |
| 数据库自动化收集 | 自动更新数据 | 符合标签、块属性、文档、块类型等条件的块会自动成为数据库条目；但不会自动在任意文档插入视图。 [^14_4][^14_5] |
| SQL / 嵌入块 | 动态展示 | 可按条件实时查询块，但它不是属性视图数据库块，也不提供数据库字段、看板等能力。 [^14_1] |
| 插件 / 模板 | 可定制 | 可通过插件或模板在特定文档中自动插入数据库块，但这是应用层扩展，不是内核的通用自动展示机制。 [^14_1] |

## 实际使用建议

1. **一个数据库，多个视图**：不要为了不同筛选条件复制数据库；应在同一 `avID` 下创建“全部 / 进行中 / 本周截止 / 已完成”等视图。[^14_2]
2. **不同文档挂不同视图**：项目文档挂“该项目相关任务”视图，每日笔记挂“今日截止”视图，总览页挂“全部任务”视图。[^14_1]
3. **避免多处直接改同一视图**：如果 A、C 两处都使用“全部任务”视图，在一处修改筛选或排序会影响另一处；需要不同展示时，请新建视图。[^14_2][^14_1]
4. **自动收集与手动插入分工**：用数据库自动化负责“哪些块进入数据库”，用数据库块负责“在哪里、以什么视图展示这些数据”。[^14_4][^14_5][^14_1]
5. **不要手改 `.sy` 创建数据库块**：官方格式文档明确提醒不要凭空构造 `AttributeViewID`，因为数据库数据需要伴随的独立属性视图文件；应使用界面、API、MCP 或 CLI。[^14_1]

一句话：**思源的数据库视图是“文档中的引用挂载点”，不是复制到文档里的静态表**；同一数据库可多处插入，多个插入点可各自选择视图，但指向同一视图时会共享其筛选、排序和字段显示配置。[^14_2][^14_1]
